# Database Design

## Overview
The SQLite schema behind `api/openapi.yaml`. Migrations are plain SQL in `crates/server/migrations/`, applied in order at startup (`design/general.md` §2). There is one file per domain, so each table's whole definition is in one place: libraries and scanning, accounts, the catalog, the change feeds, listening and searching activity, and plugins. Sections of the API not yet built add their tables as they are (§10).

---

## 1. Conventions

| | Rule |
|---|---|
| **IDs** | Random positive 63-bit integers as `INTEGER PRIMARY KEY`, drawn from the system's random source by `db::new_id` and bound to each `INSERT`, since SQLite ignores `DEFAULT` on an `INTEGER PRIMARY KEY`. A collision, about one in 10¹³ per insert at a million rows, fails its transaction rather than being retried. The API shows them as decimal strings, which clients treat as opaque. |
| **Timestamps** | Integer milliseconds since the Unix epoch, UTC, named `*_at`. Queries read them as they are, and the API formats them as RFC 3339 with milliseconds in Rust (`api/time.rs`). |
| **Durations** | Integer microseconds, named `*_us`, matching the API. Playback positions and listen time are the exception: integer milliseconds named `*_ms` (`player_states.position_ms`, `plays.listen_time_ms`), because the API carries them in milliseconds (`positionMs`, `listenTimeMs`). A track's `duration_us` holds whole milliseconds, the precision lofty, the tag reader, reports for every format. |
| **Booleans** | `INTEGER` with `CHECK (x IN (0, 1))`. |
| **Indexes** | Partial and unique indexes, feeds (ending in `seq`, named `_feed`) and sweeps (`_age`) are named for their purpose: `tracks_missing`, `tracks_file`, `library_changes_feed`, `search_events_age`. Every other index is `<table>_by_<key>`, leaving out a leading `library_id`: `tracks_by_added`, `plays_by_user`. |
| **Tables** | `STRICT`, so a column holds only its declared type. Link tables are `WITHOUT ROWID`. |
| **Ownership** | A table more than one part of the server uses is written from one module, the one that owns it, so a schema change has one place to look. It binds code as it is written or changed; SQL that breaks it is not moved just to meet it. |
| **Names** | A closed set of names is `CHECK`ed, such as `scans.trigger`. Plugin permission and hook names are not: they grow with the plugin contract, and Rust checks them (`design/plugins.md` §6). |
| **JSON** | Only for values never queried by field: settings, exclude patterns, labels, pass-through identifiers, a play's artists and genres. A query reaches rows only through indexes on ordinary columns, and may then expand an array of plain values with `json_each`; nothing in a JSON value is indexed or used to find the row that holds it, and no query looks inside an object. Always `CHECK`ed as valid and of the right shape. |
| **Secrets** | Tokens and codes are stored as SHA-256 hashes, passwords as PHC strings. Nothing secret is stored readably. |

**Why random IDs.** Sequential IDs are shared across libraries, so a user who sees track 1000 and then track 1003 learns that tracks 1001 and 1002 exist somewhere they cannot reach. That breaks "inaccessible is indistinguishable from nonexistent" (`requirements/users.md` §10). Random 64-bit IDs stay as compact as sequential ones for the catalog on device, and reveal nothing. Internal-only tables, such as `login_attempts` and the feeds, keep ordinary sequential rowids.

**An ID a client chooses is keyed with its user.** A play keeps the `playId` its device chose, so it is counted once however often it is reported (`requirements/analytics.md` §6), and any other user can choose the same one, by chance or on purpose. So `plays` is keyed by `(user_id, id)`, `play_events` refers to a play by both, and one user's report never reaches another's play.

**A signed-out device keeps its token hash.** `devices.revoked_reason` marks it signed out, so a request with its token is answered `401 session_revoked` with the reason, which tells the device whether to keep its downloads (`requirements/offline.md` §9). Its row is deleted only by the device's own `logout` or with its account. Every sign-in makes a new random token, so a revoked one never authenticates again, and a suspended account's tokens, signed out or not, answer as unknown ones do (`requirements/users.md` §10).

## 2. Isolation by Construction

**Every content table carries `library_id`, and every link between content rows is a composite foreign key on `(library_id, id)`.** A track can only reference an album, root, artist, image or biography in its own library, and a link across libraries fails at insert (`requirements/general.md` §3.6). Deleting a library cascades through everything it holds, and removes nothing outside it. A user's plays are theirs rather than the library's, so they stay, with `library_id` cleared (§6).

**`plugin_grants` and `plugin_settings` keep what applies to a plugin everywhere as library 0**, which no library can have, since `libraries.id` is `CHECK`ed above zero. So neither can reference `libraries`, and a trigger on `libraries` deletes a library's rows in both with it.

**A composite foreign key cannot use `ON DELETE SET NULL`**, because it would clear `library_id` too, which is `NOT NULL`. So the links to an image, a biography, an album, a track, or a root (`artists.image_id`, `albums.image_id`, `albums.artist_image_track_id`, `albums.biography_track_id`, `tracks.image_id`, `tracks.artist_image_id`, `tracks.biography_id`, `tracks.album_id`, `tracks.root_id`, `images.root_id`) take no action on delete, and such a row cannot be deleted while anything still refers to it, or, for an album's deferred links to its tracks (§3), while anything still refers to it when the transaction commits. Deletes run in dependency order: an album goes only once no track is left on it, and anything that deletes images or biographies must delete only those nothing refers to (nothing deletes them yet).

## 3. Derived Data the Scanner Maintains

The scanner is the only writer of content (`requirements/general.md` §3.2), so derived values are kept current in the same transaction as the change that affects them. Reads, which dominate, never recompute them.

| Derived | Stored on |
|---|---|
| Counts and durations | `libraries`, `albums`, `artists`, `tags` |
| Sort keys, computed by the shared core | Every sortable table. Tracks also copy their album's and first artist's sort key. |
| Album fields resolved from tracks — release date, disc and track totals, loudness, art, labels | `albums`, `album_discs` |
| Artist images and biographies, resolved from their tracks | `artists` |
| Displayed names: each name's most-used spelling | `artists.name`, `albums.title`, `tags.name` |
| Album artists, resolved from each file's album-artist credits, or its primary artist where it has none | `album_artists` |
| Album and artist genres | `album_tags`, `artist_tags` |

**Sort keys are copied onto tracks** because browsing pages with keyset pagination over one index (§4), and sorting tracks by artist or album would otherwise need a join at every page.

**Identity is a folded key; the displayed name is the most-used spelling.** Each artist credit is split on semicolons and folded into `artists.name_key`, which decides identity. The fold trims outer whitespace, lowercases, writes every `ς` as `σ` and every whitespace character (a tab, a no-break space) as a space, then applies NFC. Runs of spaces are kept, so `Sun  Ra` and `Sun Ra` are two artists. Lowercasing is not full case folding, so `straße` and `STRASSE` stay two artists. The folding happens in the server, because SQLite's `NOCASE` covers ASCII letters only. Albums follow the same rule: `title_key` is the title trimmed and folded, `artists_key` is the album artists' `name_key`s sorted and joined with `;`, and the two together are unique. A tag folds the same way into `tags.name_key`, with each run of whitespace inside it collapsed to one space, so `Hip  Hop` is `Hip Hop`, while `HipHop` and `Hip-Hop` are other tags (`requirements/tags.md` §4).

**A sort key is folded further than a name key.** The core makes it from the sort tag, or else from the name without a leading article, folded as a name key is, then compatibility-decomposed (NFKD), lowercased with every `ς` written `σ`, stripped of diacritics and recomposed (NFC), with each run of whitespace collapsed to one space. So `Édith` sorts as `edith`, `ＡＢＢＡ` as `abba`, and Hangul stays composed. The diacritics are the Combining Diacritical Marks, Hebrew points and cantillation, and Arabic harakat; marks that spell another script's letters or vowels, such as Devanagari vowel signs, are kept. Letters with no decomposition are written without their mark or as two letters, as library filing rules write them and as search folds them: `ø` as `o`, `ł` as `l`, `đ` and `ð` as `d`, `ı` as `i`, `æ` as `ae`, `œ` as `oe`, `ß` as `ss` and `þ` as `th`. Names that differ only in accents share a key, and the `id` that ends every sort breaks the tie (§4). Keys are stored, so once a release has shipped, a change to how the core makes them needs a migration that rewrites the stored ones.

The displayed name — `artists.name`, `albums.title`, `tags.name` — is the spelling most files use, so it follows the collection. Each track records how its file writes every name: `track_artists.artist_name`, `track_album_artists.artist_name`, `tracks.album_title`, and `track_tags.tag_name`. Names come from these without rereading files, and ties break by the spelling's bytes so a tie never flips the name between scans.

**Counts follow each change by ±1.** Triggers on tracks and their links (`0007_catalog_counts.sql`) keep every count that one change moves by one: the library's tracks, albums, artists and duration; an artist's tracks, available tracks (which follow `missing_since`), albums and appearances (which follow the album's artists); a tag's tracks, albums and artists. `album_tags` and `artist_tags` count the tracks that bring each genre, so a row goes with the last of them. Spellings are counted the same way, in `artist_spellings`, `tag_spellings`, and `artist_sort_keys` (the sort keys of the tracks crediting the artist first), and the scanner reads the top of each for the artists and tags a batch touched, since only the shared core can make a sort key from a name. So a batch's derived work is proportional to the rows it changes, however many tracks the albums, artists and tags it touches hold: albums count theirs in groups (below), and 16 tracks added to a genre of 16,000 cost what 16 in a genre of their own do. A track's artist credits and genres are deleted before the track, since the counts they feed read it, and an artist or tag is deleted when no credit or genre names it, never because a count reached zero.

**Albums are resolved from their groups.** A disc total, and each disc's track total in `album_discs`, is the largest its tracks tag, and the album's `track_total` is the sum of its discs' totals: the spec's `trackTotal`, which the API reads as stored. The title, release date and release type are the most-used values, and the sort key the first among the tracks with that title. A largest or most-used value can't be kept by ±1, so the triggers keep `album_groups` instead: an album's tracks grouped by every value the album resolves from them (disc, title as written, sort key, release date and type, track and disc totals, compilation flag), each group with how many tracks it holds, how many of them are not missing, and their duration. The scanner resolves each album a batch touched from its groups, and most albums have one per disc: 16 files added to an album of 20,000 untagged files, all in one group, took 1–2 ms to resolve where reading its tracks took 630–730 ms (laptop, debug build). An album whose tracks disagree on many values, such as loose files with no album tag that keep their own dates, has a group per combination, so it costs those, never more than its tracks. A key can't hold NULL, so a value a track lacks is `''` or `-1` in its group, values the checks on `tracks` keep any track from holding. The labels are those of its first track that has any, in the order art follows (below), and the album artists are those of its first track in album order (by disc, then track number, then id), each read from the head of an index (`tracks_with_labels`, `tracks_by_album_order`). Every track of an album credits the same album artists, since they are part of its identity, but files can list them in different orders. Album artists already in place are left alone so their counts don't churn; only when a new first track lists them in another order do the moved rows recount the artists' appearances, which reads the album's tracks. Album loudness, the duration-weighted energy mean of the analyzed tracks and their loudest peak, is read from `tracks_analyzed`, an index of the analyzed tracks alone: it costs nothing for an album nothing has analyzed, and one entry per analyzed track for the rest, the one part of an album that costs its size (16–27 ms for 20,000 analyzed tracks, where reading them took 450–510 ms). An album's `artist_sort_key` is its first album artist's sort key, so when a batch changes an artist's sort key, every album that artist heads takes the new one, touched or not; that costs the artist's albums, and only when its key changes.

**Art and biographies are resolved from tracks too.** Each track records the art its file resolved (`tracks.image_id`, embedded or a `cover.*`, with `image_embedded`), its artist image (`artist_image_id`), and its biography (`biography_id`, into `biographies`, one row per distinct text as `images` has one per distinct content). Tracks offer them in one order: present before missing, then by disc, one with none first, then by track number, one with none last, then by path and id. An album shows the first art in that order, except that among present tracks, and among missing ones, embedded art comes before any cover (`requirements/scanning.md` §3.1). It also points at its first track with an artist image and its first with a biography (`albums.artist_image_track_id`, `biography_track_id`), and an artist shows those of the first track its albums point at, the unknown artist none. Its albums are those it is an album artist of, so a guest never takes the image or biography of an album they appear on, and on an untagged album only the primary artist does. So a sidecar removed clears what only it supplied, and a changed one replaces it. All of it comes with the recompute of each album and artist a batch touched: an album's from the head of the index that holds that order for the tracks offering each (`tracks_with_art`, `tracks_with_artist_image`, `tracks_with_biography`), one entry however large the album, and an artist's from the tracks its albums point at, not every track crediting it, so Various Artists on 20,000 tracks in 2,000 albums reads 2,000 tracks by key (2 ms on a laptop, where reading all its tracks took 12–18 ms). Those reads go by id rather than as the planner's statistics suggest (§4): each album and biography through a subquery by id, which SQLite answers by id alone, and each track through a join that keeps the planner off every index on `tracks` (`NOT INDEXED`), with `CROSS JOIN` pinning the artist's albums as the outer loop. An album's `artist_sort_key` reads its first album artist through a subquery by id the same way. Left to choose, a planner whose statistics were gathered while no album offered an artist image scans every album that offers one, for each artist a batch touches: rereading 16 tracks on a 32,000-track database took 3.3 million SQLite steps rather than 67,000, a cost that grows with the library and that `PRAGMA optimize` never corrects, since it analyzes a table again only once it grows or shrinks tenfold. Statistics that describe `tracks` as a single row would still send the join to scan it; the writer never gathers those (§4). The album's links to those tracks are deferred foreign keys, so a track can go before the recompute in its transaction points the album past it.

**Per-file tags stay on the track.** Spellings, `tracks.track_total`, `disc_total`, and `labels` keep what each file says, and resolution happens once, into `album_discs` and `albums`. When tags disagree, the resolution rule lives in one place.

## 4. Pagination

**Keyset, never `OFFSET`.** A cursor encodes the last row's sort columns and `id`, and the next page is `WHERE (sort, id) > (…) ORDER BY sort, id LIMIT n`. Every browse sort has an index ending in `id`, so page 5,000 costs what page 1 does (`requirements/conventions.md` §3). Ties are broken by a meaningful column before `id` wherever they are common, since random IDs would otherwise scatter them — albums from the same year sort by name, and tracks by release date keep album order.

**Filtered browsing picks its driving side by size.** A filtered page is either a walk of the sort index that checks each row against the filter, or a lookup of the filter's rows that are then sorted. Each is fast on one side and slow on the other: at 300k tracks, a 100-track genre sorted by name takes 0.8 ms from the tag and 27 ms walking the name index, while a 100k-track genre takes 60 ms from the tag and 10 ms walking. The server chooses using the counts it already stores (`tags.track_count`, `artists.track_count`, `albums.track_count`), rather than leaving it to the planner.

**`PRAGMA optimize` runs periodically**, so the planner has statistics. Without them, the small-genre walk above took 168 ms. Statistics describe the library as it was when they were gathered, and `PRAGMA optimize` gathers them again only for a table that has grown or shrunk tenfold since, so a statement a scan batch runs reads by id where it can rather than leave the planner a choice that old statistics can make wrong (§3). **No statistics are gathered while the libraries together hold under 1,000 tracks** (`STATISTICS_FROM_TRACKS`), neither as the database opens nor at the hourly sweep. Statistics from a few tracks describe each table as a row or a few, and send the planner to scan tables that have since grown rather than look rows up: the track an album offers its artists an image from (§3), the range update that marks a vanished folder's tracks missing, following an artist's changed sort key to the albums it heads, and the triggers that count an artist's available tracks and appearances, each reading the whole table rather than the few rows it changes until the first sweep after the library grows tenfold. Without statistics the planner takes every table to be large and looks rows up. The guard counts tracks, so the last three still go wrong for a library of 1,000 tracks or more in a handful of albums or by a handful of artists, such as loose untagged files, which all share one album and one artist, until the hourly sweep after those grow tenfold.

## 5. Change Feeds

- **A change row names the entity, never its contents.** Catching up reads each changed entity's current representation, so the feed and the data cannot disagree.
- **Coalesced on write.** Recording a change deletes that entity's earlier row, so each entity has at most one row, carrying its latest position. "Everything after cursor N" is then already the net effect.
- **Tombstones age out.** Deletions leave one row. Dropping those older than the retention window advances the feed's horizon, and older cursors answer `410`. Neither the aging out nor the horizon is built yet; each feed gains its horizon column with them.
- **Written in the same transaction** as the change itself.

## 6. Personal Data

**Listening statistics are read from `plays`**, never stored as a separate truth that could drift from them (`requirements/analytics.md` §2). None is served yet; each arrives with its section of the API, with whatever index it needs.

**A play keeps a snapshot of its track**, so its history and statistics outlive the track (`requirements/analytics.md` §8, `requirements/scanning.md` §8.1). `plays` holds the track's title, duration and release date, and its artists, album and genres as the catalog names and matches them (§3): `artists` and `artist_keys` are the artists' names and `name_key`s in credit order, `album`, `album_title_key` and `album_artists_key` are the album's title and keys, and `genre_keys` are the genres' `name_key`s. The unknown artist and album are kept too, since untagged music is listened to as well: the unknown artist is a `null` name with the key `''`, and the unknown album a `NULL` title with an empty title key and its artists' key, as the catalog keys it. The same credit query, with no filter, feeds both artist arrays (`credits_json!`), and a `CHECK` holds their lengths equal, so they line up by position. The `INSERT … SELECT` that records a report reads all of it from the track it already checks.

**A snapshot keeps keys, not row IDs.** The catalog deletes an artist or album with its last track and makes a new row, under a new random ID, when its music comes back, so an ID would split one artist's plays in two. The keys are the catalog's identity: they survive a purge and a return, and the unknown artist and album have them. A statistic groups by `(library_id, key)`, and, for a play in a library the user reaches, finds the live artist, album or genre through the unique indexes on `(library_id, name_key)`, `(library_id, title_key, artists_key)` and `(library_id, type, name_key)`. A per-entity statistic expands the arrays of the user's plays it scans anyway, so it needs no link table. The cost: a change to how the core folds names must also re-fold the keys in `plays`, in the same migration that re-folds the catalog's. It can re-fold artist and album-title keys from the stored names, and genre and album-artist keys from the keys themselves, which works only when the new folding folds more.

**A later report refreshes the snapshot**, which improves "last known" only for the few plays reported again after a retag, but costs nothing, since the row is rewritten anyway. A report that names another track than the play's changes nothing of it. Once the track is purged no report finds it, so the play keeps what it last had. `plays.track_id` has no foreign key, so a purge never deletes a play, and random IDs (§1) make it vanishingly unlikely that a purged track's ID is ever another track's.

**History shows a user's own plays wherever they were heard.** It reads the live track through `LEFT JOIN tracks ON tracks.id = p.track_id AND tracks.library_id = p.library_id`, only in libraries the user reaches; any other play, purged or out of reach, shows its snapshot, marked unavailable, with `trackId: null`. History leaves the unknown artist's `null` out of the API's `snapshot.artists`, so it stays a list of names. Deleting a library clears its plays' `library_id` (`ON DELETE SET NULL`), since `libraries.id` can be used again and a new library must not inherit them; its `play_events` go with it, so no hook delivers them. Such a play is never found by a report again, and appears only in views across all libraries, as does a play in a library the user can no longer reach (`requirements/analytics.md` §8). Every read treats a play whose library the user does not reach exactly as a library-less one: no live join, `libraryId` null, the same `availability` as a purged track, and grouped under `(NULL, key)`. Otherwise a revoked library would show through: history would name it where a deleted one is null, and a statistic would join its live entities (`requirements/users.md` §10). Every read is by `user_id`, which keys `plays` (§1), so no other user ever sees them. An admin viewing an account's history or statistics (`requirements/analytics.md` §9) sees exactly what that user sees, these plays included, with reach judged as that user's.

**Hooks that act for one user read their domain's outbox** (`design/general.md` §4), written by the same transaction as the activity:

- `play_events` holds each play's start and end, for `playing` and `played`, with a `kind` and one sequence. The feed index `play_events_feed` is keyed `(library_id, user_id, kind, seq)`, so each hook's due check and batch read one range of its own kind, as `library_changes_kind_feed` does for the change hooks. A position caught up on ends never steps over later starts, nor the reverse, though ends pile up when a device catches up after being offline. Stale starts are swept on each new play through `play_events_started_age`, a partial index on starts alone, so the sweep never reads an end. Ends go at 30 days through `play_events_ended_age` (§9).
- `search_events` names each search or forget, and keeps what a search found. Rows are written only for a user who shares their searches, and only then is the search index asked to count, so no one else's search pays for it.

**A user's connection to a plugin is one row of `plugin_connections`**, keyed by plugin and user and the same in every library: their personal settings, when they connected, and `searches_shared_at`, null until they share their searches with it. Sharing is a column of the connection rather than a table of its own, so it can never exist without one, and disconnecting deletes both. Settings are kept as entered, secrets included, because the plugin needs them; the API never returns the secrets (`design/plugins.md` §7). A connection goes with its user, and with the plugin: unlike grants and settings, which are keyed by the plugin's ID and outlive an uninstall, it references `plugins`, so its users connect again after a reinstall (`0006_plugins.sql`, `design/plugins.md` §6).

## 7. State and Cache

| In the database (`data/state/`) | Rebuildable (`data/cache/`) |
|---|---|
| Everything above | Resized images |
| Waveforms and loudness — analysis takes days to redo | Search indexes |
| | Transcodes |

**Every connection must enable `PRAGMA foreign_keys = ON`.** SQLite leaves foreign keys off by default, and §2 depends on them.

Migrations are the exception: they run with foreign keys off, because rebuilding a parent table with them on deletes or clears every reference to it. Each migration commits only if `PRAGMA foreign_key_check` finds no broken reference anywhere in the database. A rebuild creates the new table, copies the rows, drops the old one and renames the new one into place, then recreates the old table's indexes, the triggers on it, and the triggers that write into it.

**Foreign keys on large tables are indexed.** Deleting a parent row checks every table referencing it, and an unindexed child column means a full scan per deleted row — deleting 200 images took 1.25 s scanning albums and artists, and 1 ms with `image_id` indexed. Small account tables skip the index, since scanning dozens of rows costs nothing. A track's links to its art, artist image and biography, and an album's to the tracks offering its artists theirs, are indexed only where set (`WHERE image_id IS NOT NULL`), which the checks still use, since `image_id = ?` rules out `NULL`. `plays.library_id` is not indexed: its parent goes only with a whole library, whose catalog cascade dwarfs one scan of `plays`.

**Each connection keeps up to 128 prepared statements.** The statements the store, the catalog recompute, the change feed, the sweep and the busiest reads repeat go through rusqlite's statement cache (`prepare_cached`), so each is compiled once per connection rather than on every run: a cold scan of 10,000 tracks (debug build, laptop) took 6.4 s of writer time rather than 19.2 s. rusqlite's default of 16 holds fewer than the store's statements alone, or than the variants of sort, order and part the keyset lists build; past 128, the cache drops the least recently used. SQL built with `format!` is cached only where its variants are few and fixed, such as one per column. A cached statement holds its compiled program: a track-page statement takes about 40 KB, so a reader's full cache holds at most about 5 MB, and the writer's track upsert, with the triggers it fires, takes about 132 KB.

**Readers map the database file into memory** (`PRAGMA mmap_size`), so a page is read from the operating system's page cache, which every reader shares, rather than copied into each reader's own 2 MB cache. At 500k tracks a 1,000-row track page took 10.4 ms rather than 14.8 ms. Each reader maps up to 1 GiB, about the database of a 500k-track library, which costs address space, not memory, on the 64-bit servers Jewelcase ships for (`design/general.md`). SQLite reads the rest of the file, or all of it if a mapping fails, as it would without the map. The cost is that an I/O error in the mapped part, such as a failing disk, stops the server with `SIGBUS` rather than failing one read.

**The writer cuts the write-ahead log back to 64 MiB** (`PRAGMA journal_size_limit`). SQLite reuses the log rather than shrinking it, so a cold scan's log would otherwise hold its largest size on disk for good. With the limit, once a checkpoint lets the log start over, the next commit cuts it back to 64 MiB. Only the writer writes the log, so only the writer sets it.

## 8. Scanning State

**Scans and their problems are library administration, so they live in `0001_libraries.sql` beside the library they belong to.** A `scans` row mirrors the API's `Scan` object, including the resume cursor the scanner writes at every batch (`design/scanning.md` §9). Problems are two tables: `scan_problem_groups`, one row per distinct `(kind, root, normalized detail)` with a count, and `scan_problems`, one row per path, deleted when the path next scans or lists cleanly, or is gone (`design/scanning.md` §8, §13).

**A scan row keeps its paths relative to their roots**, as tracks do, so no storage path is stored. Each scope in `scans.scopes` names its root by ID and its folder relative to that root, `cursor_dir` is relative to the root of the scope the cursor is in, and `current_root_id` and `current_path` name the folder being scanned. A cursor folder whose path is not UTF-8 is kept as its nearest ancestor that is, since a lossy spelling could sort past folders not yet scanned. A resume from that ancestor walks the folders between it and the real cursor again, so the scan's progress counts can run high, though only for a scan interrupted at such a name. A scan interrupted while its root was repointed resumes at the root's new path. The scopes are resolved against the library's active roots, so a scan whose root has been removed cannot resume, and its row is marked suspended as an unreadable one is.

**Reconciliation compares each folder's listing with the index, one folder at a time.** As a scan lists a folder, it reads what the index holds directly in it in one pass over `tracks_file` in path order: a row directly in the folder is a file, and the first row under a folder below names that folder, past whose rows the read then seeks. The read costs a seek per indexed folder and a step per file, however much lies below, and holds only what is directly in the folder, as large as the listing the scan already holds. It serves the skip check of every file in the folder, which compares each row's size, mtime and `sidecar_stamp` (`design/scanning.md` §2), and what the listing no longer shows goes missing in the batch with the folder's files: a track whose file is gone with its own `UPDATE` and feed entry, and a folder gone with one range `UPDATE ... RETURNING id` over its subtree (`design/scanning.md` §7–§8). An unchanged file writes nothing. Recording on each file that a scan saw it would write about 4 KB of log per file, 2 GB per rescan at 500k, since the value changes on every scan on rows keyed at random. A folder that cannot be listed is never reconciled, and its parent's listing still names it, so a scan resumed after a crash needs no memory of what it could not read.

**The analysis queue is the start of one index.** `tracks.analyzer_version` is the version of the analyzer whose results a track holds: 0 until it is analyzed, and again once a scan finds its file's size or mtime changed (`design/scanning.md` §12), never `NULL`. The queue is then `analyzer_version < current`, and a new analyzer version needs no rewrite of any row. `tracks.file_mtime` is `NULL` while a track's file has changed and not been read since (`design/scanning.md` §8), and the queue leaves such a track for a scan to read first. `tracks_unanalyzed` holds the tracks not missing and with a known mtime in the order the queue is worked, `(library_id, analyzer_version, added_at DESC, id)`: tracks never analyzed before those an older analyzer did, and the newest first within each (`design/scanning.md` §12). A pick reads the first rows of one range and sorts nothing. At 500k tracks it takes under 0.1 ms however much is analyzed, where sorting the library by `added_at` takes 300–550 ms once half of it is, and as long for the idle poll once all of it is.

**Tracks carry no content fingerprint yet.** The scanner keys on path until track identity is settled, and the fingerprint column arrives with that design (`design/scanning.md` §6). `images.placeholder` is `NULL` until the placeholder job decodes the file into a ThumbHash, and empty when it cannot; the scanner fills the dimensions and hash from the header. An image is one row per content in its library, found by its hash, and its path is wherever a scan last found that content, so art still loads after its folder is renamed.

## 9. Retention

**One sweep, every hour, on the writer**, starting five minutes after the database opens, so a server restarted often still sweeps, and just before `PRAGMA optimize` (§4), so the statistics it gathers count what is left (`crates/server/src/db/retention.rs`). What is kept for a while goes once it is older than 30 days:

| Rows | Kept |
|---|---|
| `scans` | 30 days after they finished. Each library keeps its last finished scan, which the admin sees, and its last completed one, which says the library has been scanned, so its next startup scan is not taken for its first (`design/scanning.md` §9). Unfinished scans stay. |
| `login_attempts` | 30 days, through `login_attempts_age`, so admins can still see an account under pressure. While an account's success from an origin is kept, its limit there counts only that origin's failures (`login_attempts_signed_in`), so failures elsewhere cannot lock its owner out there. Anyone who shares that origin, or claims it from the private network (`api/origin.rs`), still gets only the account's free attempts there. |
| `play_events` ends | 30 days, delivered or not, through `play_events_ended_age`. Starts over an hour old go as each new play is recorded (§6), so they stay few. |
| `recent_searches`, and `search_events` other than `stopped` | 30 days (`requirements/search.md` §6). Until the sweep reaches them, the list of recent searches leaves out those past the window. |
| `search_events` `stopped` | Until the plugin's `searched` position for that user in that library reaches it, however long that takes, or the plugin is uninstalled. |
| Missing `tracks` | 30 days after `missing_since` (`requirements/scanning.md` §8). |
| `images`, `biographies` | While a track, album or artist uses the image, or a track the biography. Artists keep a copy of a biography's text, not a reference to it. |

A hook that cannot deliver for 30 days misses what aged out meanwhile: ends for `played`, finished scans for `scanFinished`, searches for `searched` (`design/hooks.md` §5). Problems need no sweep, since each is deleted when its path scans or lists cleanly, or is gone (§8), and the feed's tombstones wait for its horizon (§5).

**A purge is a change like any scan's.** The sweep deletes a missing track in the same transaction as the recompute of the albums, artists and tags it counted toward (§3), which deletes those it was the last of, and records each deletion in the feed, so clients drop them. The recompute is what lets the transaction commit: `albums.artist_image_track_id` and `biography_track_id` are deferred foreign keys, and an album still pointing at a purged track fails the commit. A play of a purged track keeps its snapshot (§6). Playlists are not modelled yet (§10); when they are, a track in one is kept, since playlist membership is the only reference that extends retention. An admin's immediate cleanup is not built.

**Each step holds the writer for about 50 ms.** The sweep is a chain of transactions, each sweeping one kind of row. A step deletes in chunks until 50 ms have passed, as long as a scan batch holds the writer (`design/scanning.md` §7), then commits, and the writer runs whatever was queued meanwhile before the next step, so a write waits for one step at most, never the whole sweep. Chunks are 100 rows, except tracks, which go 16 at a time, the smallest batch a scan writes: with its recompute, which reads each album it touches whole, a purged track costs about 2 ms in a debug build. Purging a whole 100,000-track library (debug build, laptop; albums of 10 tracks, artists of 5 albums) took 3,027 steps over 204 s, a mean of 67 ms, 117 ms at the 99th percentile and 252 ms at most, where chunks of 100 tracks, purging 20,000, took a mean of 167 ms and up to 385 ms. Images and biographies are walked by ID, 100 rows at a time, so no step reads either table whole. A step that fails or panics is rolled back, and the sweep passes over that kind of row until the next hour, so a row that cannot go never holds up the others.

**Resized copies stay.** The image cache (§7) is named by content hash, which another library's image can share, and is rebuilt on demand, so the sweep leaves the copies of an image it deletes in `cache/images`.

## 10. Not Yet Modelled

Playlists, queues, mixes, downloads, the job queue, external sources, the audit log, user settings, invites, password resets, the account change feed, and the completion-weighted score behind `sort=top`. Each arrives with its section of the API.

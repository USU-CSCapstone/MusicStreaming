# Database Design

## Overview
The SQLite schema behind `api/openapi.yaml`. Migrations are plain SQL in `crates/server/migrations/`, applied in order at startup (`design/general.md` §2). There is one file per domain, so each table's whole definition is in one place: libraries and scanning, accounts, the catalog, the change feeds, listening and searching activity, plugins, and playlists. Sections of the API not yet built add their tables as they are (§10). Until the first release, migrations are edited in place, so a data directory made with an older development schema must be recreated; from the release on, they are append-only.

---

## 1. Conventions

| | Rule |
|---|---|
| **IDs** | Random positive 63-bit integers as `INTEGER PRIMARY KEY`, drawn from the system's random source by `db::new_id` and bound to each `INSERT`, since SQLite ignores `DEFAULT` on an `INTEGER PRIMARY KEY`. A collision, about one in 10¹³ per insert at a million rows, fails its transaction rather than being retried. The API shows them as decimal strings, which clients treat as opaque. |
| **Timestamps** | Integer milliseconds since the Unix epoch, UTC, named `*_at`. Queries read them as they are, and the API formats them as RFC 3339 with milliseconds in Rust (`api/time.rs`). |
| **Durations** | Integer microseconds, named `*_us`, matching the API. Playback positions and listen time are the exception: integer milliseconds named `*_ms` (`player_states.position_ms`, `plays.listen_time_ms`), because the API carries them in milliseconds (`positionMs`, `listenTimeMs`). A track's `duration_us` holds whole milliseconds, the precision lofty, the tag reader, reports for every format. |
| **Booleans** | `INTEGER` with `CHECK (x IN (0, 1))`. |
| **Indexes** | Partial and unique indexes, feeds (ending in their position column, such as `seq` or `position`, named `_feed`) and sweeps (`_age`) are named for their purpose: `tracks_missing`, `tracks_file`, `library_changes_feed`, `search_events_age`. Every other index is `<table>_by_<key>`, leaving out a leading `library_id`: `tracks_by_added`, `plays_by_user`. |
| **Tables** | `STRICT`, so a column holds only its declared type. Link tables are `WITHOUT ROWID`. |
| **Ownership** | A table more than one part of the server uses is written from one module, the one that owns it, so a schema change has one place to look. It binds code as it is written or changed; SQL that breaks it is not moved just to meet it. |
| **Names** | A closed set of names is `CHECK`ed, such as `scans.trigger`. Plugin permission and hook names are not: they grow with the plugin contract, and Rust checks them (`design/plugins.md` §6). |
| **JSON** | Only for values never queried by field: settings, exclude patterns, labels, a track's listing of its album artists, pass-through identifiers, a play's artists and genres. A query reaches rows only through indexes on ordinary columns, and may then expand an array of plain values with `json_each`; nothing in a JSON value is indexed or used to find the row that holds it, and no query looks inside an object. The one exception is `album_groups`, whose key copies a track's `labels` and `album_artist_ids` whole, as written, with `''` for no labels, so an album counts the tracks carrying each (§3); the writer always spells the same array the same way. Always `CHECK`ed as valid and of the right shape, the `album_groups` copies through the track columns they copy. |
| **Secrets** | Tokens and codes are stored as SHA-256 hashes, passwords as PHC strings. Plugin credentials are stored as entered, since the plugin must send them: never returned or logged, and only in the `state` folder, which the server creates for its own user alone (`requirements/plugins.md` §6). |

**Why random IDs.** Sequential IDs are shared across libraries, so a user who sees track 1000 and then track 1003 learns that tracks 1001 and 1002 exist somewhere they cannot reach. That breaks "inaccessible is indistinguishable from nonexistent" (`requirements/users.md` §10). Random 64-bit IDs stay as compact as sequential ones for the catalog on device, and reveal nothing. Internal-only tables, such as `login_attempts`, keep ordinary sequential rowids. The feeds keep one too, `seq`, for coalescing and the plugins' positions, but clients never see it: the API carries each feed's own `position` (§5).

**An ID a client chooses is keyed with its user.** A play keeps the `playId` its device chose, so it is counted once however often it is reported (`requirements/analytics.md` §6), and any other user can choose the same one, by chance or on purpose. So `plays` is keyed by `(user_id, id)`, `play_events` refers to a play by both, and one user's report never reaches another's play.

**A signed-out device keeps its token hash.** `devices.revoked_reason` marks it signed out, so a request with its token is answered `401 session_revoked` with the reason, which tells the device whether to keep its downloads (`requirements/offline.md` §9). Its row is deleted only by the device's own `logout` or with its account. Every sign-in makes a new random token, so a revoked one never authenticates again, and a suspended account's tokens, signed out or not, answer as unknown ones do (`requirements/users.md` §10).

## 2. Isolation by Construction

**Every content table carries `library_id`, and every link between content rows is a composite foreign key on `(library_id, id)`.** A track can only reference an album, root, artist, image or biography in its own library, and a link across libraries fails at insert (`requirements/general.md` §3.6). Deleting a library cascades through everything it holds, and removes nothing outside it. A user's plays are theirs rather than the library's, so they stay, with `library_id` cleared (§6).

**`plugin_grants` and `plugin_settings` keep what applies to a plugin everywhere as library 0**, which no library can have, since `libraries.id` is `CHECK`ed above zero. So neither can reference `libraries`, and a trigger on `libraries` deletes a library's rows in both with it.

**A composite foreign key cannot use `ON DELETE SET NULL`**, because it would clear `library_id` too, which is `NOT NULL`. So the links to an image, a biography, an album, a track, or a root (`artists.image_id`, `albums.image_id`, `tracks.image_id`, `tracks.artist_image_id`, `tracks.biography_id`, `tracks.album_id`, `tracks.root_id`, `images.root_id`) take no action on delete, and such a row cannot be deleted while anything still refers to it. Deletes run in dependency order: an album goes only once no track is left on it, and anything that deletes images or biographies must delete only those nothing refers to (nothing deletes them yet).

## 3. Derived Data the Scanner Maintains

The scanner is the only writer of content (`requirements/general.md` §3.2), so derived values are kept current in the same transaction as the change that affects them. Reads, which dominate, never recompute them.

| Derived | Stored on |
|---|---|
| Counts and durations | `libraries`, `albums`, `artists`, `tags` |
| Sort keys, computed by the shared core | Every sortable table. Tracks also copy their album's and first artist's sort key. |
| Album fields resolved from tracks — release date, disc and track totals, loudness, art, labels | `albums`, `album_discs` |
| Artist images and biographies, resolved from their tracks | `artists` |
| Displayed names: each name's most-used spelling | `artists.name`, `albums.title`, `tags.name` |
| Album artists, resolved from each file's album-artist credits, or its primary artist where it has none | `album_artists` |
| Album and artist tags, of every type | `album_tags`, `artist_tags` |
| Playlist artwork, from the art of the albums its first items are on | `playlists.image_key` (§6) |

**Sort keys are copied onto tracks** because browsing pages with keyset pagination over one index (§4), and sorting tracks by artist or album would otherwise need a join at every page. A track copies its album's and its first artist's keys as resolved, never its file's own, so an album or artist whose files disagree on a sort tag sorts as one run. The store copies them as it writes the track, and follows a changed key onto the tracks that copy it, which costs those tracks, only when the key changes: a trigger (`0007_catalog_counts.sql`) for an album's, through the album's tracks in `tracks_by_album_order`, and the recompute for an artist's, which writes each album the artist heads and each track crediting it first by id, since a statement choosing them with `IN` was planned as a scan of every album or track on statistics gathered over a few (§4). **Known cost:** an artist whose files split nearly evenly between two sort tags can take the other key when a few of its tracks are added or removed, and each such flip rewrites every track crediting it first in the batch that flips it, tens of thousands for an artist as large as §4's giant one. **Known cost:** plugins see an album's title on each of its tracks and an artist's name on each of its albums, so an album whose displayed title flips to another spelling records every track of the album on the change feed, and a renamed artist every album it is an album artist of, in the batch that flips it, even when no sort key moved; each record reads the entity once to fingerprint it (§5), so the flip costs the album's tracks or the artist's albums, as a sort-key flip does. Each file's own keys stay beside the copies, in `file_album_sort_key`, `file_artist_sort_key` and `file_album_artist_sort_key`, which the album's groups and `artist_sort_keys` count.

**Identity is a folded key; the displayed name is the most-used spelling.** Each artist credit is split on semicolons and folded into `artists.name_key`, which decides identity. The fold trims outer whitespace, lowercases, writes every `ς` as `σ` and every whitespace character (a tab, a no-break space) as a space, then applies NFC. Runs of spaces are kept, so `Sun  Ra` and `Sun Ra` are two artists. Lowercasing is not full case folding, so `straße` and `STRASSE` stay two artists. The folding happens in the server, because SQLite's `NOCASE` covers ASCII letters only. Albums follow the same rule: `title_key` is the title trimmed and folded, `artists_key` is the album artists' `name_key`s sorted and joined with `;`, and the two together are unique. A tag folds the same way into `tags.name_key`, with each run of whitespace inside it collapsed to one space, so `Hip  Hop` is `Hip Hop`, while `HipHop` and `Hip-Hop` are other tags (`requirements/tags.md` §4).

**Tag types are rows, not a `CHECK`.** `tag_types` lists every type the scanner reads, server-wide, with the name it is shown by, the plugin that added it, the field it is read from, and the generation of tag types it was added in (none of them for genre and mood), since a type is a field files carry whichever library they are in, and `tags.type` references it, so a new type is an insert (`requirements/tags.md` §2). Tags are unique per library on `(type, name_key)`, so `Ambient` the genre and `Ambient` the mood are two tags. Genre's and mood's fields are the tag mapper's (`design/scanning.md` §4), not the database's, and a plugin's type is read from its row as each scan starts. `tag_generation`, one row, counts the changes to what a scan reads, a release's new built-in type included, and never falls, even as a type is removed; each track records the generation it was read with, `tracks.tags_generation`, so a scan reads it again when a type is added (`design/scanning.md` §2).

**A sort key is folded further than a name key.** The core makes it from the sort tag, or else from the name without a leading article (a tag keeps its article, so `A Cappella` sorts under A), folded as a name key is, then compatibility-decomposed (NFKD), lowercased with every `ς` written `σ`, stripped of diacritics and recomposed (NFC), with each run of whitespace collapsed to one space. So `Édith` sorts as `edith`, `ＡＢＢＡ` as `abba`, and Hangul stays composed. The diacritics are the Combining Diacritical Marks, Hebrew points and cantillation, and Arabic harakat; marks that spell another script's letters or vowels, such as Devanagari vowel signs, are kept. Letters with no decomposition are written without their mark or as two letters, as library filing rules write them and as search folds them: `ø` as `o`, `ł` as `l`, `đ` and `ð` as `d`, `ı` as `i`, `æ` as `ae`, `œ` as `oe`, `ß` as `ss` and `þ` as `th`. Names that differ only in accents share a key, and the `id` that ends every sort breaks the tie (§4). Keys are stored, so once a release has shipped, a change to how the core makes them needs a migration that rewrites the stored ones.

The displayed name — `artists.name`, `albums.title`, `tags.name` — is the spelling most files use, so it follows the collection. Each track records how its file writes every name: `track_artists.artist_name`, `track_album_artists.artist_name`, `tracks.album_title`, and `track_tags.tag_name`. Names come from these without rereading files, and ties break by the spelling's bytes so a tie never flips the name between scans.

**Counts follow each change by ±1.** Triggers on tracks and their links (`0007_catalog_counts.sql`) keep every count that one change moves by one: the library's tracks, albums, artists and duration; an artist's tracks, available tracks (which follow `missing_since`) and albums it is an album artist of; a tag's tracks, albums and artists. `album_tags` and `artist_tags` count the tracks that bring each tag, and `album_credits` the tracks of an album that credit each artist, so a row goes with the last of them. An artist's owned tracks, appearances (credits on tracks of albums that do not list it) and albums under any credit are not stored: they are counted when asked, from the artist's `album_artists`, `album_groups` and `album_credits` rows, which costs the artist's albums (0.3–2.6 ms for an artist of 1,270 albums at 500k tracks, about 0.1 ms for most, on a laptop) and which `album_credits` keeps from costing the artist's credited tracks (counting those of an artist with 14,000 tracks directly took 14–20 ms). Statements that update artists for each credit of a track read the credits as the table they update from (`UPDATE artists SET … FROM track_artists c WHERE c.track_id = … AND artists.id = c.artist_id`), which SQLite plans by the track whatever statistics it has, where a `WHERE id IN (SELECT …)` was planned as a scan of every artist on statistics gathered over a few. Spellings are counted the same way, in `artist_spellings`, `tag_spellings`, and `artist_sort_keys` (the sort keys of the tracks crediting the artist first, as artist or as album artist: as artist by `ARTISTSORT`, as album artist by `ALBUMARTISTSORT`. A file votes at most once for an artist: where its first album artist is its first artist, including when the album artist falls back to the primary artist, it votes only as artist, with `ARTISTSORT`, else `ALBUMARTISTSORT`. A different album artist without `ALBUMARTISTSORT`, and the unknown artist, cast no vote, so only a tag can outvote an artist's own: a composer credited only as album artist still has its tag counted, and an untagged credit never outvotes the `ARTISTSORT` the artist is tagged with elsewhere), and the scanner reads the top of each for the artists and tags a batch touched, since only the shared core can make a sort key from a name. So a batch's derived work is proportional to the rows it changes, however many tracks the albums, artists and tags it touches hold: albums count theirs in groups (below), and 16 tracks added to a genre of 16,000 cost what 16 in a genre of their own do. A track's artist credits, album artist credits and genres are deleted before the track, since the counts they feed read it, and an artist or tag is deleted when no credit or genre names it, never because a count reached zero.

**`libraries.names_version` moves only with what search indexes.** Triggers in the same file bump it whenever a track, album or artist is added, deleted or renamed, and nothing else does, so analysis, art and every other write leave a library's in-memory search index as it is. A search that finds the version moved since its index was built starts a rebuild in the background (`crates/server/src/api/search/indexes.rs`).

**Albums are resolved from their groups.** A disc total, and each disc's track total in `album_discs`, is the largest its tracks tag, and the album's `track_total` is the sum of its discs' totals: the spec's `trackTotal`, which the API reads as stored. A track with no disc number counts as disc 1 there and in the album's `disc_count`, so its total is not added again, though `album_discs` keeps its own row for it, which the API shows as a disc numbered `null`. The title and release date are the most-used values, the type the one more than half the album's tracks name in their release-type tags, however each spells it, if any (`requirements/albums.md` §3), and the sort key the first among the tracks with that title. A largest or most-used value can't be kept by ±1, so the triggers keep `album_groups` instead: an album's tracks grouped by every value the album resolves from them (disc, title as written, sort key as the file gives it, release date and type, track and disc totals, compilation flag, labels, and the order the file lists the album artists in, `tracks.album_artist_ids`), each group with how many tracks it holds, how many of them are not missing, and their duration. The scanner resolves each album a batch touched from its groups, and most albums have one per disc: 16 files added to an album of 20,000 untagged files, all in one group, took 1–2 ms to resolve where reading its tracks took 630–730 ms (laptop, debug build). An album whose tracks disagree on many values, such as loose files with no album tag that keep their own dates, has a group per combination, so it costs those, never more than its tracks. A key can't hold NULL, so a value a track lacks is `''` or `-1` in its group, values the checks on `tracks` keep any track from holding. Every track of an album credits the same album artists, since they are part of its identity, but files can list them in different orders. The labels and the album artists' order are most-used values too, ties broken by bytes as the others' are. A track with no labels counts toward none (its group holds `''`), and labels are compared as the file lists them: `["A","B"]` and `["B","A"]`, or two spellings of one label, are different sets. The album artists are written from the winning listing's ids (`json_each`). Album artists already in place are left alone so their counts don't churn; only when another order becomes the most used are the moved rows rewritten. Album loudness, the duration-weighted energy mean of the analyzed tracks and their loudest peak, is read from `tracks_analyzed`, an index of the analyzed tracks alone: it costs nothing for an album nothing has analyzed, and one entry per analyzed track for the rest, the one part of an album that costs its size (16–27 ms for 20,000 analyzed tracks, where reading them took 450–510 ms). An album's `artist_sort_key` is its first album artist's sort key, so when a batch changes an artist's sort key, every album that artist heads takes the new one, touched or not; that costs the artist's albums, and only when its key changes.

**Art and biographies are resolved from tracks too.** Each track records the art its file resolved (`tracks.image_id`, embedded or a `cover.*`, with `image_embedded`), its artist image (`artist_image_id`), and its biography (`biography_id`, into `biographies`, one row per distinct text as `images` has one per distinct content). Tracks offer art in one order: present before missing, then by disc, one with none first, then by track number, one with none last, then by path and id. An album shows the first art in that order, except that among present tracks, and among missing ones, embedded art comes before any cover (`requirements/scanning.md` §3.1). An artist shows the image and biography of a present track on the first of its albums that has one, the unknown artist none, and a track missing offers neither. Which album is first is not defined, only that the same data gives the same answer. Its albums are those it is an album artist of, so a guest never takes the image or biography of an album they appear on, and on an untagged album only the primary artist does. So a sidecar removed clears what only it supplied, and a changed one replaces it. All of it comes with the recompute of each album and artist a batch touched: an album's from the head of the index that holds that order for the tracks offering art (`tracks_with_art`), one entry however large the album, and an artist's from its albums, stopping at the first track found, so it costs the artist's albums at most. Each of the artist's two reads is pinned rather than left to the planner's statistics (§4): `CROSS JOIN` keeps the artist's albums as the outer loop, and `INDEXED BY` names a partial index of the present tracks that offer (`tracks_with_artist_image`, `tracks_with_biography`, each on `album_id`), so an album is one lookup. An album's `artist_sort_key` reads its first album artist through a subquery by id. The pin is insurance rather than a fix for a plan seen failing: it makes each album one probe of its index and fixes the order the pick is taken in, whatever the statistics (§4).

**Per-file tags stay on the track.** Spellings, `tracks.track_total`, `disc_total`, `labels` and the file's sort keys keep what each file says, and resolution happens once, into `album_discs` and `albums`. When tags disagree, the resolution rule lives in one place.

## 4. Pagination

**Keyset, never `OFFSET`.** A cursor encodes the last row's sort columns and `id`, and the next page is `WHERE (sort, id) > (…) ORDER BY sort, id LIMIT n`. Every browse sort has an index ending in `id`, so page 5,000 costs what page 1 does (`requirements/conventions.md` §3). Ties are broken by a meaningful column before `id` wherever they are common, since random IDs would otherwise scatter them — albums from the same year sort by name, and tracks by release date keep album order.

**A page filtered by artist starts from the artist's credits.** It reads the IDs the artist is credited on as the filter asks, owned, featured or either, looks each row up by id and sorts them, with `CROSS JOIN` fixing that order rather than leaving it to the planner. Owned albums come from `album_artists` and albums a track credits the artist on from `album_credits`; owned tracks are the tracks of the owned albums, and tracks that credit the artist come from `track_artists`. Without an artist filter, an album filter is a condition on `album_id`, which `tracks_by_album_order` serves; with one, it is checked on each of the artist's tracks. A page costs what the artist holds, so a giant artist is slow: one owning about 15% of a 500k-track library, such as 77k tracks, takes about 100 ms a page on the Ryzen 7 2700X. That cost is accepted unless it shows up in use.

**A page filtered by tag starts from the tag's rows when they are few, and walks the sort's index otherwise** (`requirements/tags.md` §7). Each list's tags of each type are a group the rows must match: all of `tagAll`'s, and any of `tagAny`'s, so all and any can mix within one type. A filter names at most 100 tags, since each is a term of the query that reads the rows and SQLite refuses more than 500 joined by `INTERSECT`. Starting from a group reads its rows from `*_tags_by_tag` and sorts them, so it costs what the group holds; walking checks each row of the sort's index against the group with one lookup of the row's own links, so a page costs what it takes to find a page's worth, which is little for a common tag and the whole index for a rare one. The smallest group leads when its stored counts say it holds at most one row in 128 of the list (`LEAD_SHARE`); every other group is checked on each row. A queue's recipe reads its list whole (`tracks::resolve`), so walking there reads the whole index and a group leads up to one row in 8 (`RESOLVE_SHARE`): at 500,000 tracks, leading resolved a tag of 4,881 tracks in 6.5 ms against 130 ms walking and one of 49,025 in 72–100 ms against 157 ms, and lost from a quarter of the library on, 416 ms against 180 ms for 144,386 tracks; at 100,000 tracks, a tag of 1,003 tracks took 1.3 ms against 21 ms. Measured on the generated library (`benchmark_tag_filters`, release build, on an Apple M5), a page of 100 tracks by name at 500,000 tracks took 0.1 ms from a tag of 6 tracks and 49 ms walking for it, 3.1 ms and 4.1 ms for a tag of 3,710, 3.9 ms and 3.6 ms for one of 4,881, and 67 ms and 2.6 ms for one of 144,386: the two cross near 4,300 tracks, one in 115, and at 100,000 tracks near 1,200, one in 80. The crossover grows more slowly than the library, but across that range one share stays within a millisecond of it, where choosing wrongly further out costs tens. An artist filter keeps the lead, since an artist's credits are usually the smaller set, and the tags are checked. A tag the library does not have makes the filter match nothing. A list of tags narrowed by name (`listTags`' `q`) tests each tag of the list it walks, with the query folded as a tag's sort key is, so its cost is the number of tags of that type, which stays small beside the tracks. Search, which ranks in memory, takes the filter as the IDs of each kind it searches that carry the tags, read from the smallest group's rows and checked against the others, so a search costs what that group holds beside the match itself; the core then ranks and counts only those (`Index::search_within`). Those IDs are kept in memory (`TaggedSets`) for the last four filters searched, by library, tags and kinds, until the library's change feed moves past the position they were read at: every change to what a row carries writes to the feed, and its positions are never reused. A search typed a letter at a time keeps its filter, so it reads a tag's rows once. A search for `track`, which every generated title matches, took 4.3 ms unfiltered at 500,000 tracks; narrowed to a tag of 144,386 tracks it took 18 ms reading the tag each time and 7.7 ms with the tag's rows kept, the rest being the check of each matching title.

**A page's `total` is a count read, not the page's rows, where one covers its filter.** An unfiltered list takes the library's stored count, and a list filtered by artist the artist's: owned albums `album_count`; the other counts, owned and featured tracks and featured albums, are read from the artist's credits as above, and either is the sum of owned and featured. A list filtered by one tag and nothing else takes the tag's count. So a page counts its rows only where no count covers its filter, such as an album's tracks, alone or by one artist, or several tags.

**`PRAGMA optimize` runs periodically**, so the planner has statistics. Without them, a walk of the name index for a 100-track genre at 300k tracks took 168 ms rather than 27. The writer runs it as the database opens and every two minutes (`OPTIMIZE_EVERY`), checking every table: it gathers statistics again for a table that lacks them or has grown or shrunk tenfold since they were gathered, and otherwise only reads each table's size, a few milliseconds. Every run reads only part of each large index (SQLite's analysis limit), so even a first open of a large database without statistics stays quick. Statistics describe the library as it was when they were gathered, so a statement a scan batch runs reads by id where it can rather than leave the planner a choice that old statistics can make wrong (§3). **A reader plans with the statistics there were when it opened**, as the server started, until the server restarts; only the writer, which gathers them, plans with newer ones. **No statistics are gathered while the libraries together hold under 1,000 tracks** (`STATISTICS_FROM_TRACKS`), neither as the database opens nor later. Statistics from a few tracks describe each table as a row or a few, and send the planner to scan tables that have since grown rather than look rows up: the track an album offers its artists an image from (§3), which reads every album that offers one until the writer's next run after the library grows tenfold. Without statistics the planner takes every table to be large and looks rows up. The guard counts tracks, so that still goes wrong for a library of 1,000 tracks or more in a handful of albums or by a handful of artists, such as loose untagged files, which all share one album and one artist, until those grow tenfold.

## 5. Change Feeds

- **A change row names the entity, never its contents.** Catching up reads each changed entity's current representation, so the feed and the data cannot disagree.
- **Coalesced on write.** Recording a change deletes that entity's earlier row, so each entity has at most one row, carrying its latest position. "Everything after cursor N" is then already the net effect.
- **Each feed counts its own positions.** `seq` numbers every library's changes in one sequence, and every account's in another, so its jumps would tell a client about libraries and accounts it cannot reach (`requirements/users.md` §10). The API, its hints and the snapshot header carry `position` alone, and never `seq`: recording a change moves the feed owner's `feed_head` (`libraries.feed_head`, `users.feed_head`) on by one and gives the row that value, so a feed's positions run 1, 2, 3 with its own changes alone, and its head is a stored counter that only grows. `seq` stays for coalescing, the hints' internal tracking and the plugins' positions, which are internal. The feeds are indexed `(library_id, position)` and `(user_id, position)`.
- **A position belongs to a run of the server.** Each start draws a random epoch (`feed_epochs`) and keeps every feed's head at that moment (`library_feed_starts`, `account_feed_starts`), which is where the run before ended. A client sends the epoch of its latest page with its position, and the server goes on only from a run it knows and a position no further than that run reached: the next start's kept head, or the feed's head for the current run (`feed::continues`). A restored backup does not know the runs after it and kept the head of the run it was taken in as of the copy, so a device ahead of the backup is refused with `410` rather than silently skipping what the restored server records next. The kept heads grow by a row per library and per account each start.
- **Tombstones age out.** Deletions leave one row. Dropping those older than the retention window advances the feed's horizon, and older cursors answer `410`. Neither the aging out nor the horizon is built yet; each feed gains its horizon column with them.
- **Written in the same transaction** as the change itself.
- **Plugins have a position of their own on each row.** `plugin_seq` is the position of the last change to the entity that changed what plugins see of it (`design/hooks.md` §1.3): each upsert stores a fingerprint of the entity's plugin view (`plugin_view`), and one that matches the row it replaces keeps that row's `plugin_seq` (`plugin_since`). The change hooks read `library_changes_plugin_feed`, `(library_id, entity_type, plugin_seq)`; devices read `position` and never see the plugin columns.
- **An embedded summary follows its entity's own change.** A track's summary embeds its album's title and art, its artists' names and its tags' names, but a change to the album, artist or tag names only that album, artist or tag, never every track that embeds it. A device keeps no copies to patch: its tables are normalized, as the server's are, so a track's summary is a join and an album change needs no track rows.

**The device's copy of the catalog.** A device follows these feeds to keep its own copy of each library ([`web.md`](web.md#catalog-worker)).

- **The library feed is served as `GET /libraries/{id}/changes?after=<position>&epoch=<epoch>&limit=`.** It returns the changes in order, each with its position, whether it is an upsert or a delete, its kind and ID, and for an upsert the device rows that represent the entity, plus the position to continue from, the feed's head and the current epoch. Positions stay integers, apart from the epoch, because a device compares them: with a hint, with `head`, and with a snapshot's. `limit` is the API's usual one (100 by default, at most 1,000). `after=0` is the whole catalog, since every entity has one row. It has the access gate of every library endpoint, so a library out of reach is `404`. A cursor older than the horizon, past the feed's head (a server that was wiped or replaced), or of an epoch the server cannot go on from (a restore), answers `410 cursor_expired`, which a device treats as a full resync. An `after` above 0 without an epoch is one it cannot go on from. The horizon itself is not built, and no tombstone is dropped yet.
- **Rows are objects keyed by device column name**, the same names the snapshot uses, so a client ignores a column it does not know and a new column breaks nobody. An entity's rows carry what it shows: a track brings its artists, tags and image references, an album its artists, credits, discs and tags. An entity that others show is put back on the feed when it changes: a changed image, tag type or sort key records the albums, artists and tracks that carry it.
- **A snapshot file serves a first sync.** `GET /libraries/{id}/catalog` returns a SQLite file of the library in the device schema, gzipped, with its feed position in `X-Jewelcase-Position` and the epoch of the run it was built in in `X-Jewelcase-Epoch`. The server builds it in one read transaction that also reads the position, so the two agree, writes it with `journal_mode=DELETE` and a fixed page size, and gathers the planner's statistics into it with `ANALYZE` (a device never gathers its own, and without them a tag-filtered page reads several times slower). It serves the database file as built, not a `VACUUM INTO` copy, which is 3.5% smaller on the wire but another write of the whole file on every build, dear on a Pi's SD card. It keeps and serves only the gzip, as `application/gzip` with no `Content-Encoding`, since a browser undoes an encoding before a page sees the bytes and could then never ask for the rest of a download by its offset. So `Range` and `If-Range` apply to the bytes the device stores, and a download cut short resumes. It serves the file only after one `quick_check` passes on the database, with the gzip's SHA-256 as its ETag: the ETag names the bytes sent, as `If-Range` needs, and the device checks it over the bytes it stored as it inflates them into its database, where gzip's checksum covers the inflating; the device never runs `quick_check`. The first request for a library answers `503 catalog_building` with `Retry-After` while the file is built.
- **One file per library, shared by every account that reaches it**, since a library's content does not depend on the account. It is kept in `cache/catalog/<library>/`, named for the device schema version, the epoch and feed position and its hash, so a release that changes the schema never serves an old file, and a file the database cannot go on from, such as one newer than a restored backup, is built again rather than served. It is rebuilt in the background once the feed has moved more than a tenth of the library's entities past it, with the old file served meanwhile. At 500,000 tracks the database is about 360 MB, 120 MB gzipped, and the build takes 20 to 50 s; importing it takes 2 to 3 s in a browser, where applying feed changes costs 1 to 3 ms each; a build needs the database and its gzip at once, and keeps the gzip alone.
- **A catch-up that would change more than a tenth of a library downloads the snapshot again.** Applying that many rows one by one is far slower than importing a file and holds the device's worker. The device counts the changes it has actually pulled, not the distance in positions: positions count repeated touches of one entity, so distance would overstate a catch-up that touched a few entities often. It never imports a snapshot at or before its own position.
- **The account feed is `account_changes`**, one coalesced row per playlist and per playlist item, written in the same transaction as the change. A deleted playlist leaves one tombstone and drops its item rows. Only the owner has rows, since playlists are personal. `GET /me/changes?after=&epoch=` returns the caller's own rows, at positions of the account's own, for libraries they reach, so catching up after one item edit costs one item. Upgrading fills it with the playlists that already exist, so a device syncs them too. Plays, queues and kept queues can join it later, each as a new kind.
- **The device schema** is the server's catalog tables with the same names and types, minus paths, roots, file stamps, scan and analysis state, plugin data and other accounts' data ([`general.md` §3.1](general.md#31-the-catalog-queries)). Images travel as an ID with their size and placeholder. The device's `libraries` table holds only the count columns the shared queries read, with no name, root or path, since the server keeps those counts by trigger. Its `playlists` table has `user_id`, always the caller's own, so one query filters by owner on both databases. The snapshot response also carries `X-Jewelcase-Schema`, the device schema version, and `Cache-Control: no-store`. A snapshot carries no playlists: a device pulls the account feed from the start whenever it installs a library's file.
- **Library changes reach every account that reaches the library**, as a hint to pull the feed ([`general.md` §5](general.md#5-realtime)).

## 6. Personal Data

**Listening statistics are read from `plays`**, never stored as a separate truth that could drift from them (`requirements/analytics.md` §2). None is served yet; each arrives with its section of the API, with whatever index it needs.

**A play keeps a snapshot of its track**, so its history and statistics outlive the track (`requirements/analytics.md` §8, `requirements/scanning.md` §8.1). `plays` holds the track's title, duration and release date, and its artists, album and genres as the catalog names and matches them (§3): `artists` and `artist_keys` are the artists' names and `name_key`s in credit order, `album`, `album_title_key` and `album_artists_key` are the album's title and keys, and `genre_keys` are the genres' `name_key`s. The unknown artist and album are kept too, since untagged music is listened to as well: the unknown artist is a `null` name with the key `''`, and the unknown album a `NULL` title with an empty title key and its artists' key, as the catalog keys it. The same credit query, with no filter, feeds both artist arrays (`credits_json!`), and a `CHECK` holds their lengths equal, so they line up by position. The `INSERT … SELECT` that records a report reads all of it from the track it already checks.

**A snapshot keeps keys, not row IDs.** The catalog deletes an artist or album with its last track and makes a new row, under a new random ID, when its music comes back, so an ID would split one artist's plays in two. The keys are the catalog's identity: they survive a purge and a return, and the unknown artist and album have them. A statistic groups by `(library_id, key)`, and, for a play in a library the user reaches, finds the live artist, album or genre through the unique indexes on `(library_id, name_key)`, `(library_id, title_key, artists_key)` and `(library_id, type, name_key)`. A per-entity statistic expands the arrays of the user's plays it scans anyway, so it needs no link table. The cost: a change to how the core folds names must also re-fold the keys in `plays`, in the same migration that re-folds the catalog's. It can re-fold artist and album-title keys from the stored names, and genre and album-artist keys from the keys themselves, which works only when the new folding folds more.

**A later report refreshes the snapshot**, which improves "last known" only for the few plays reported again after a retag, but costs nothing, since the row is rewritten anyway. A report that names another track than the play's changes nothing of it. Once the track is purged no report finds it, so the play keeps what it last had. `plays.track_id` has no foreign key, so a purge never deletes a play, and random IDs (§1) make it vanishingly unlikely that a purged track's ID is ever another track's.

**History is to show a user's own plays wherever they were heard.** No history is served yet. It is to read the live track through `LEFT JOIN tracks ON tracks.id = p.track_id AND tracks.library_id = p.library_id`, only in libraries the user reaches; any other play, purged or out of reach, is to show its snapshot, marked unavailable, with `trackId: null`, and to leave the unknown artist's `null` out of the API's `snapshot.artists`, so it stays a list of names. Deleting a library clears its plays' `library_id` (`ON DELETE SET NULL`), since `libraries.id` can be used again and a new library must not inherit them; its `play_events` go with it, so no hook delivers them. Such a play is never found by a report again, and appears only in views across all libraries, as does a play in a library the user can no longer reach (`requirements/analytics.md` §8). Every read is to treat a play whose library the user does not reach exactly as a library-less one: no live join, `libraryId` null, the same `availability` as a purged track, and grouped under `(NULL, key)`. Otherwise a revoked library would show through: history would name it where a deleted one is null, and a statistic would join its live entities (`requirements/users.md` §10). Every read is by `user_id`, which keys `plays` (§1), so no other user ever sees them. An admin viewing an account's history or statistics (`requirements/analytics.md` §9) is to see exactly what that user sees, these plays included, with reach judged as that user's.

**Hooks that act for one user read their domain's outbox** (`design/general.md` §4), written by the same transaction as the activity:

- `play_events` holds each play's start and end, for `playing` and `played`, with a `kind` and one sequence. The feed index `play_events_feed` is keyed `(library_id, user_id, kind, seq)`, so each hook's due check and batch read one range of its own kind, as `library_changes_plugin_feed` does for the change hooks. A position caught up on ends never steps over later starts, nor the reverse, though ends pile up when a device catches up after being offline. Stale starts are swept on each new play through `play_events_started_age`, a partial index on starts alone, so the sweep never reads an end. Ends go at 30 days through `play_events_ended_age` (§9).
- `search_events` names each search or forget, and keeps what a search found. Rows are written only for a user who shares their searches, and only then is the search index asked to count, so no one else's search pays for it.

**An account's queues are `queues`, `queue_list_uses` and `queue_lists`** (`design/queue.md` §1, §5, §7). `queues`, keyed `(user_id, queue_id)`, holds each queue's state as JSON without its lists, its `version` and `context`, whether it is `active`, and, for a parked one, `last_active` and `position`. A partial unique index, `queues_active`, allows one active row per account. `queue_list_uses` says which lists each queue uses and cascades with the queue, so one statement finds the account's lists no queue uses. `queue_lists`, keyed `(user_id, hash)`, holds each list once per account as a BLOB of 8-byte little-endian track IDs, hashed with SHA-256 as the hash names them, and cascades with the account. It is not `WITHOUT ROWID`, so a page of rows can read single IDs from a stored list by incremental BLOB I/O. It has no foreign key on `library_id`: a deleted library's tracks are simply not found, as in `plays`. Four things write them, each as a job on the writer: the background save (`queue/save.rs`), every second for each changed account, in one savepoint per account, so a failure rolls back that account alone, which writes first the queues parked since the last save (kept with `active = 0`, `last_active` and `position` if adjusted, deleted otherwise), then the lists, then the active row, first demoting any other active row of the account, so a stale or unreadable one cannot hold the one-active index; a restore, which makes a kept queue active and saves the account at once; a delete; and the hourly expiry (§9, `db/retention.rs`); the rest are in `queue/keep.rs`. A start is only a change to memory, which the next save writes; an active-queue row is upserted with `ON CONFLICT DO UPDATE`, never replaced, since a replace would quietly delete a clashing row.

**Player state names a queue item.** `player_states.item_id` is the item, `<key>.<position>`, the playing device last reported, with `position_ms`. It has no foreign key: a new queue replaces the active one without touching it, and the state keeps naming its item until the next report. A report is accepted only if the account's active queue holds the item.

**A user's connection to a plugin is one row of `plugin_connections`**, keyed by plugin and user and the same in every library: their personal settings, when they connected, and `searches_shared_at`, null until they share their searches with it. Sharing is a column of the connection rather than a table of its own, so it can never exist without one, and disconnecting deletes both. Settings are kept as entered, secrets included, because the plugin needs them; the API never returns the secrets (`design/plugins.md` §7). A connection goes with its user, and with the plugin: unlike grants and settings, which are keyed by the plugin's ID and outlive an uninstall, it references `plugins`, so its users connect again after a reinstall (`0006_plugins.sql`, `design/plugins.md` §6).

**A playlist is its user's own, in one library** (`0008_playlists.sql`, `requirements/playlists.md`). `playlists` is keyed by a random ID and carries `library_id` and `user_id`, and every read and write of one filters by both, so another account, an admin included, finds it as absent as one that never was (`requirements/users.md` §10). Its `version` starts at 1 and every change adds 1, and its `track_count` and `duration_us` count every item, missing tracks included, and are written in the same transaction as the items. `folded` is the title as search folds it, which the list's name filter looks inside, and `sort_key` is the core's key for it.

**A playlist's artwork is an ID kept on its row.** `playlists.image_key` is the ID `getImage` serves: the first album image among the playlist's items in key order (the album's `image_id`, through the track) when it has one to three distinct ones, `m<a>-<b>-<c>-<d>` for the first four, and NULL for none. Create and any edit with ops recompute it in the same write, by reading items in key order and stopping at the fourth distinct image (`db/catalog/art.rs`), so the read is the playlist's start unless few of its tracks have art; an edit of the details alone leaves it. The ID changes exactly when the first four distinct covers do, so reordering later tracks or adding another track of an album already shown leaves it. Unlike `track_count`, it follows the library too, since it names images a scan can delete: the recompute a scan batch or a purge runs (§3) recomputes it, in the same transaction, for each playlist holding a track the batch moved onto another album (`playlist_items_by_track`) or a track of an album whose art changed (`tracks_by_album_order`, then the same index), so a replaced, added or removed cover, or a track retagged onto another album, moves it on, and it never names an image that is gone. That costs a probe per moved track, and each playlist found its start, or more when few of its items have art. **Known cost:** an album whose art changes costs a probe per track it holds, in the batch that changes it, which for an album as large as §4's is tens of thousands; only a changed cover pays it. It moves neither `version` nor `modified_at`, since the user changed nothing, so an edit made meanwhile is not refused. The scanner writes no other column of a playlist. A single image's placeholder is read through the key; a mosaic has none.

**Pinned playlists come first in either order.** `pin_rank` is a generated column, 1 for a pinned playlist and NULL for the rest. A list's keyset puts it first, with `Unknown::Null`, so the pinned are the known part and the rest the unknown part, which keyset paging already reads after the known one in both orders (§4). Each sort has an index on `(user_id, library_id, pin_rank, <key>, id)`: `playlists_by_name`, `playlists_by_created`, `playlists_by_modified`. A user has hundreds of playlists at most, so the page's total is counted from the same index range rather than stored.

**Items are rows under sparse keys.** `playlist_items` is keyed `(playlist_id, key)`, `WITHOUT ROWID`, so a playlist's items in order are one range of its key, even at 50,000. Keys start `KEY_GAP` = 2^20 apart; an item put or moved between two takes the midpoint, and a playlist whose gap is used up is renumbered, so an edit writes the rows it changes and never the playlist (see *An edit is one write*). An item carries `library_id`, and both its links are composite foreign keys on `(library_id, …)`: a playlist's items must be in its library, and so must their tracks (§2). The playlist link cascades, so deleting a playlist deletes its items in the same statement. The track link does not: retention keeps a track an item names (§9), so it never dangles. `playlist_items_by_track` serves that check and the reverse question, which playlists hold a track.

**An edit is one write, proportional to the change.** `editPlaylist` does its work off the writer, on a read snapshot: it checks the version, expands the adds, loads the playlist's `(key, track_id, added_at)` rows (one range of the primary key), applies the ops in memory with the shared core's `apply_ops`, and works out the rows to delete and insert and the totals after (`edit::plan`). Then one `try_write` checks the version again, writes only those rows, and sets the details, counts, `version + 1` and `modified_at`; it never applies ops, so the writer is held for writes that scale with the change, however many ops the edit has. Every change to the items moves the version, so a playlist still at the edit's version holds the rows the plan was made from. A version other than the edit's, at either check, is `409 version_conflict`, an op out of range `422`, and either writes nothing. Retention keeps the tracks a playlist holds (§9), so the one thing that can go stale between the read and the write is a track the edit adds being purged: the write looks each added track up again and, if one is gone, writes nothing and the edit is planned again, leaving it out as any purged track is left out of an add. Which rows to write comes from the keys the items carry after the ops (`api/playlists/keys.rs`): a longest increasing run of the stored keys stays where it is, and every other item, moved or added, takes a key between its kept neighbours (evenly spread, so one item takes the midpoint, `KEY_GAP` apart past either end). Removed and moved rows are deleted first and the moved and added ones inserted after, so a new key never meets an old one that is on its way out. When a gap between neighbours is too small, or a key would overflow, the whole playlist is deleted and reinserted at `KEY_GAP` spacing in that same write; each item keeps its `added_at`. `createPlaylist` writes its items the same way, as one add to the new, empty playlist, inside its write. `track_count` and `duration_us` are recounted from the items the plan loads, joined to `tracks.duration_us`, so they reflect track durations as of the playlist's last create or edit of its items: an edit of the details alone leaves them, and a rescan that changes a duration does not update them (the scanner touches only a playlist's artwork).

**An idempotency key remembers the answer of a request that applied.** `idempotency_keys` is keyed `(user_id, key)` and holds the status and body that `createPlaylist` or `editPlaylist` answered, written in the same transaction as the change, so a crash cannot apply one without the other. A retry with the same key finds it before expanding anything and again inside the write, where a concurrent first attempt would be, and gets that answer. A refused request writes nothing, so its key can be reused. Keys are per user, not per playlist or operation. The hourly sweep deletes them after 24 hours, not the 30-day window (§9), through `idempotency_keys_by_age`.

**An items page is one read of one version.** `listPlaylistItems` pages by keyset on the primary key, `key > ?` with `LIMIT`, and its cursor carries the playlist's `version` and the last key. The version check, the rows and the track summaries are read in one snapshot, so a page is one version; a cursor made at another version answers `410 cursor_expired` and the client starts again, since a key says nothing about position once items were added or moved. `total` is the stored `track_count`. A duplicate is a separate item, so summaries are read once per distinct track and mapped back onto the rows. The duplicates check expands the request's items, then looks each distinct track up in `playlist_items_by_track` (`library_id, track_id` leading, the playlist ID in the covering index), so its cost follows the request, not the playlist.

## 7. State and Cache

| In the database (`data/state/`) | Rebuildable (`data/cache/`) |
|---|---|
| Everything above | Resized images |
| Waveforms and loudness — analysis takes days to redo | Search indexes |
| | Library catalog files for devices (`cache/catalog/`) |
| | Transcodes |

**Resized images are kept per library**, as `cache/images/<library>/<first byte of the hash>/<hash>-<size>.jpg`. A playlist mosaic is kept beside them, as `cache/images/<library>/m/<user>/<id>-<id>-<id>-<id>-<size>.jpg`, in the folder of the user it was made for: `getImage` reads each of the four IDs in the caller's library (any that is not there, or has no file, is `404`, so an ID naming another library's images is a foreign image's), composes a 2×2 grid of squares cropped to fill, no larger than the first size that holds twice the longest cover, and keeps it under the IDs, which change with the images' content. A mosaic ID is accepted only as four canonical IDs that equal the `image_key` of one of the caller's own playlists in the library (an indexed read of the caller's playlists), so the mosaics that can be made are bounded by what playlists hold, and another user's artwork is as absent as a foreign one; each user has their own copies, so a cache hit says nothing of another user's playlists. Two libraries holding the same artwork each keep a copy, so how fast an image is answered says nothing of what another library has viewed (`requirements/general.md` §3.6). A request's size rounds up to the next fixed size, and no further than the first that holds the whole image, which is never enlarged, so an image has a handful of copies at most. An image ffmpeg refuses leaves a `.failed` marker, so it is not tried again on every request until the server next starts, which forgets every failure, since one may pass: a file read just as a tagger rewrote it, or ffmpeg failing on a host short of memory. A file that does not open, or that went away as ffmpeg read it, as on a share that dropped, leaves no marker, and a missing one answers `404`. A copy is written to a temporary file and renamed into place. As the server starts, before it takes requests, it deletes the copies of images no library holds, the mosaics that name one or that no playlist of the user they were made for has as its artwork any more, the folders of libraries that are gone, every failure marker, and the temporary files of renders a crash cut short. Artwork a scan replaces keeps its copies until the next start, and so do the mosaics of playlists whose artwork a scan moved on. A playlist's mosaics go sooner: after an edit of items or a delete commits, off the request and best effort (a failure is logged), the server deletes the user's mosaics in that library, failure markers included, that none of their playlists there has as its artwork, so repeated edits cannot grow the cache; the start-up sweep catches what a crash or a failed delete missed.

**Every connection must enable `PRAGMA foreign_keys = ON`.** SQLite leaves foreign keys off by default, and §2 depends on them.

Migrations are the exception: they run with foreign keys off, because rebuilding a parent table with them on deletes or clears every reference to it. Each migration commits only if `PRAGMA foreign_key_check` finds no broken reference anywhere in the database. A rebuild creates the new table, copies the rows, drops the old one and renames the new one into place, then recreates the old table's indexes, the triggers on it, and the triggers that write into it.

**Foreign keys on large tables are indexed.** Deleting a parent row checks every table referencing it, and an unindexed child column means a full scan per deleted row — deleting 200 images took 1.25 s scanning albums and artists, and 1 ms with `image_id` indexed. Small account tables skip the index, since scanning dozens of rows costs nothing. A track's links to its art, artist image and biography are indexed only where set (`WHERE image_id IS NOT NULL`), which the checks still use, since `image_id = ?` rules out `NULL`. `plays.library_id` is not indexed: its parent goes only with a whole library, whose catalog cascade dwarfs one scan of `plays`.

**Each connection keeps up to 128 prepared statements.** The statements the store, the catalog recompute, the change feed, the sweep and the busiest reads repeat go through rusqlite's statement cache (`prepare_cached`), so each is compiled once per connection rather than on every run: a cold scan of 10,000 tracks (debug build, laptop) took 6.4 s of writer time rather than 19.2 s. rusqlite's default of 16 holds fewer than the store's statements alone, or than the variants of sort, order and part the keyset lists build; past 128, the cache drops the least recently used. SQL built with `format!` is cached only where its variants are few and fixed, such as one per column. A cached statement holds its compiled program: a track-page statement takes about 40 KB, so a reader's full cache holds at most about 5 MB, and the writer's track upsert, with the triggers it fires, takes about 132 KB.

**Readers map the database file into memory** (`PRAGMA mmap_size`), so a page is read from the operating system's page cache, which every reader shares, rather than copied into each reader's own 2 MB cache. At 500k tracks a 1,000-row track page took 10.4 ms rather than 14.8 ms. Each reader maps up to 1 GiB, about the database of a 500k-track library, which costs address space, not memory, on the 64-bit servers Jewelcase ships for (`design/general.md`). SQLite reads the rest of the file, or all of it if a mapping fails, as it would without the map. The cost is that an I/O error in the mapped part, such as a failing disk, stops the server with `SIGBUS` rather than failing one read.

**The writer cuts the write-ahead log back to 64 MiB** (`PRAGMA journal_size_limit`). SQLite reuses the log rather than shrinking it, so a cold scan's log would otherwise hold its largest size on disk for good. With the limit, once a checkpoint lets the log start over, the next commit cuts it back to 64 MiB. Only the writer writes the log, so only the writer sets it.

## 8. Scanning State

**Scans and their problems are library administration, so they live in `0001_libraries.sql` beside the library they belong to.** A `scans` row holds a scan's state, trigger, scopes and progress counts, including the resume cursor the scanner writes at every batch (`design/scanning.md` §9). Problems are two tables: `scan_problem_groups`, one row per distinct `(kind, root, normalized detail)` with a count, and `scan_problems`, one row per path, deleted when the path next scans or lists cleanly, or is gone (`design/scanning.md` §8, §13).

**A scan row keeps its paths relative to their roots**, as tracks do, so no storage path is stored. Each scope in `scans.scopes` names its root by ID and its folder relative to that root, `cursor_dir` is relative to the root of the scope the cursor is in, and `current_root_id` and `current_path` name the folder being scanned. A cursor folder whose path is not UTF-8 is kept as its nearest ancestor that is, since a lossy spelling could sort past folders not yet scanned. A resume from that ancestor walks the folders between it and the real cursor again, so the scan's progress counts can run high, though only for a scan interrupted at such a name. A scan interrupted while its root was repointed resumes at the root's new path. The scopes are resolved against the library's active roots, so a scan whose root has been removed cannot resume, and its row is marked suspended as an unreadable one is.

**Reconciliation compares each folder's listing with the index, one folder at a time.** As a scan lists a folder, it reads what the index holds directly in it in one pass over `tracks_file` in path order: a row directly in the folder is a file, and the first row under a folder below names that folder, past whose rows the read then seeks. The read costs a seek per indexed folder and a step per file, however much lies below, and holds only what is directly in the folder, as large as the listing the scan already holds. It serves the skip check of every file in the folder, which compares each row's size, mtime and `sidecar_stamp` (`design/scanning.md` §2), and what the listing no longer shows goes missing through the scan's batches, each track with its own `UPDATE` and feed entry: one whose file is gone, and every one under a folder gone, which the same read finds a folder at a time down its subtree (`design/scanning.md` §7–§8). An unchanged file writes nothing. Recording on each file that a scan saw it would write about 4 KB of log per file, 2 GB per rescan at 500k, since the value changes on every scan on rows keyed at random. A folder that cannot be listed is never reconciled, and its parent's listing still names it, so a scan resumed after a crash needs no memory of what it could not read.

**The analysis queue is the start of one index.** `tracks.analyzer_version` is the version of the analyzer whose results a track holds: 0 until it is analyzed, and again once a scan finds its file's size or mtime changed (`design/scanning.md` §12), never `NULL`. The queue is then `analyzer_version < current`, and a new analyzer version needs no rewrite of any row. `tracks_unanalyzed` holds the tracks not missing in the order the queue is worked, `(library_id, analyzer_version, added_at DESC, id)`: tracks never analyzed before those an older analyzer did, and the newest first within each (`design/scanning.md` §12). A pick reads the first rows of one range and sorts nothing. At 500k tracks it takes under 0.1 ms however much is analyzed, where sorting the library by `added_at` takes 300–550 ms once half of it is, and as long for the idle poll once all of it is.

**Tracks carry no content fingerprint yet.** The scanner keys on path until track identity is settled, and the fingerprint column arrives with that design (`design/scanning.md` §6). `images.placeholder` is `NULL` until the placeholder job decodes the file into a ThumbHash, and empty when it cannot; the scanner fills the dimensions and hash from the header. An image is one row per content in its library, found by its hash, and its path is wherever a scan last found that content, so art still loads after its folder is renamed.

## 9. Retention

**One sweep, every hour**, a task that starts five minutes after the server does, so a server restarted often still sweeps, and that stops between chunks when the server stops (`crates/server/src/db/retention.rs`). What is kept for a while goes once it is older than 30 days, but for idempotency keys, which go after a day:

| Rows | Kept |
|---|---|
| `scans` | 30 days after they finished. Each library keeps its last finished scan, which the admin sees, and its last completed one, which says the library has been scanned, so its next startup scan is not taken for its first (`design/scanning.md` §9). Unfinished scans stay. |
| `login_attempts` | 30 days, through `login_attempts_age`, so admins can still see an account under pressure. While an account's success from an origin is kept, its limit there counts only that origin's failures (`login_attempts_signed_in`), so failures elsewhere cannot lock its owner out there. Anyone who shares that origin, or claims it from a trusted proxy's address (`api/origin.rs`), still gets only the account's free attempts there. |
| `play_events` ends | 30 days, delivered or not, through `play_events_ended_age`. Starts over an hour old go as each new play is recorded (§6), so they stay few. |
| `recent_searches`, and `search_events` other than `stopped` | 30 days (`requirements/search.md` §6). Until the sweep reaches them, the list of recent searches leaves out those past the window. |
| `search_events` `stopped` | Until the plugin's `searched` position for that user in that library reaches it, however long that takes, or the plugin is uninstalled. |
| Missing `tracks` | Never while a playlist holds one (§6); otherwise 30 days after `missing_since`, through `tracks_missing`, keyed by root so the walk of one root never reads another's marks, and then until a scan of the track's whole root that started after those 30 days has completed (`library_roots.walked_at`), finding it still missing (`requirements/scanning.md` §8). A scan of a folder confirms nothing, nor does one that suspends, as a scan of an unmounted root does, so a mark that a dropped share or a scan's mistake left is never purged before the root has been walked again. **Known cost:** while one root of a library with several is unmounted, every scan of the whole library suspends and its retry requests only that root, so no walk of the other roots completes either, and their missing tracks wait for the purge until it returns. That keeps rows longer, never deletes one early. |
| `idempotency_keys` | 24 hours, through `idempotency_keys_by_age`, in chunks like the rest (§6). |
| Kept `queues` | 30 days after `last_active`, the day the queue was parked, for those with `active = 0`; the lists no queue uses go after them, 8 at a time, since a list is up to 4 MB. A parked queue not yet saved is still `active = 1` in the database, so the sweep never takes it, and a restore and the sweep are each one write on the writer, so a restore finds the row or finds it gone (`queue/keep.rs`). Expiry sends nothing to devices. |
| `images`, `biographies` | While a track, album or artist uses the image, or a track the biography. Artists keep a copy of a biography's text, not a reference to it. |

A hook that cannot deliver for 30 days misses what aged out meanwhile: ends for `played`, finished scans for `scanFinished`, searches for `searched` (`design/hooks.md` §5). Problems need no sweep, since each is deleted when its path scans or lists cleanly, or is gone (§8), and the feed's tombstones wait for its horizon (§5).

**A purge is a change like any scan's.** The sweep deletes a missing track in the same transaction as the recompute of the albums, artists and tags it counted toward (§3), which deletes those it was the last of, and records each deletion in the feed, so clients drop them. A play of a purged track keeps its snapshot (§6). A track that any playlist holds is not purged (`playlist_items_by_track`, §6), whoever's playlist it is and however long the track has been missing, since playlist membership is the only reference that extends retention; it goes once no playlist holds it. **Known cost:** each sweep of a root passes over the missing tracks playlists hold before it reaches the others, so a library with many such tracks pays for them in every chunk. An admin's immediate cleanup is not built.

**Each chunk is one write.** The sweep goes through the kinds of row in turn and queues one write per chunk until the kind has none left, so the writer runs whatever else is queued between chunks, and a write waits for one chunk at most, never the whole sweep. Chunks are 100 rows, except tracks, which go 16 at a time, half a scan batch (`design/scanning.md` §7): with its recompute, which resolves each album it touches from its groups (§3), a purged track costs about 1 ms in a release build on a laptop, so purging 50,000 missing tracks is minutes of writer time that must not be one write. In an sqlite3 experiment on a laptop, deleting 300,000 login attempts in one statement took 3.1 s, where chunks of 1,000 rows took 89 ms each; chunks of 100 are shorter still. Images and biographies are walked by ID, 100 rows at a time, so no write reads either table whole. A write that fails or panics is rolled back, and the sweep passes over that kind of row until the next hour, so a row that cannot go never holds up the others.

**Resized copies go at the next start.** The sweep leaves the copies of an image it deletes in the image cache (§7), which deletes them itself as the server next starts.

# Jewelcase web client

The responsive web app: Svelte 5 + TypeScript on SvelteKit in SPA mode (`design/general.md` §1, §7.1).

## Running it

The client talks only to the public API (`api/openapi.yaml`), and `vite dev` and `vite preview`
forward `/api` (the realtime connection included) to a running server: `http://localhost:8080`, or
`API_PROXY` if set. So start the server on a music folder, then the client.

```sh
# 1. From the repository root. Waveforms and loudness come from analysis, which runs in the
#    background and starts about 30 seconds after launch.
JEWELCASE_MUSIC=/path/to/music JEWELCASE_DATA_DIR=./data cargo run -p jewelcase-server

# 2. In another terminal, start the client.
cd web
pnpm install
pnpm dev            # http://localhost:5173
```

The server must be running: without it the page loads, but every API request fails with `502`.

`docker compose up` runs both, with the client reloading as the source changes.

## Catalog worker

The device keeps a copy of every library it can reach, in SQLite on the browser's private file system, so pages, search and queue building work offline ([ADR 0008](../adr/0008-sqlite-device-catalog.md), `design/general.md` §3.1). `src/lib/api/client.ts` stays the one module pages call: it sends catalog reads to `catalog/read.ts`, which asks the worker and gets the JSON the server would send.

- **One owner tab.** The browser's file handle for the database belongs to one dedicated worker and is exclusive, so each tab asks for one Web Lock, and the tab that holds it runs the catalog worker (`client.svelte.ts`). The other tabs send their requests to it over a `BroadcastChannel` and get answers back (`router.ts`), and the queue worker reaches the catalog the same way. A request with no answer when a new owner announces itself is sent again. The owner opens the database only after it holds the lock and releases the pool before it gives the lock up. A new owner opens the files with retries, since the old one may still be closing; Chromium releases a terminated worker's files at once (a new worker opened them in about 75 ms after one was killed mid-apply, within the first try). When the owner closes, the browser hands the lock to another tab. An owner whose tab is hidden hands over only to a waiting tab that is in view, and only while no snapshot is downloading: tabs tell each other over the channel when an owner is hidden and when a tab in view waits, so on a desktop with several tabs a switch to another site, or to a tab that is not waiting for the catalog, leaves the worker where it is. A waiting tab that goes out of view leaves the queue for the lock and joins it again when shown, so the lock only ever passes to a tab in view; a tab out of view takes it only when no one holds it. This is needed because no browser sends `pagehide` for a tab switch and iOS sends nothing when a tab goes to the background. An owner also lets go when Chromium freezes its page, stopping its worker without waiting for it so the lock is released before the freeze, and takes part again when the page resumes. A tab that was signed in at its last visit joins the election before its first page loads (`preconnect`), so a launch at a deep link offline finds the device's copy coming. The owner gives the lock up if its worker has not opened the files within 20 seconds, then joins the election again behind any tab waiting, so a tab alone tries again, and it waits 3 seconds for the worker to release the pool before it stops it anyway.
- **Tabs hold the owner's state instead of asking for it** (`router.ts`, `protocol.ts`). The owner publishes `{ protocol: 2, user, serving, heavy, libraries }` on the `jewelcase-catalog` channel. `libraries` holds, for each library, whether it is on the device, whether a catch-up is being applied to it, whether its search index is built and, if its snapshot was left for want of room, what that needs. The worker sends it whenever it changes, and the owner publishes it when it starts serving, when it stops (`serving: false`, before it lets go of the pool) and when a tab that has just joined asks with `who`, as a tab restored from the back/forward cache or unfrozen also does, since it may have missed what was published meanwhile. Every tab keeps the last state as reactive state, so whether a library is on the device, whether its index is built and what the account page lists are read with no request. `heavy` is set while the worker is inside one call that holds it for seconds, a snapshot install's copy or an index build, and online reads skip the device meanwhile. A tab treats an owner that is not serving, or serves another account, as no owner; the owner itself refuses a query from another account's tab and leaves the election if its own session has gone. The worker answers only `busy`, whether a snapshot is downloading, ahead of its queue of work.
- **A request is answered only to the tab that asked.** It carries an ID and the name of the asker's own reply channel (`jewelcase-catalog-reply-<random>`), and the owner answers on that channel alone, so no other tab or worker hears the answer. The owner keeps a reply channel open until it has been idle for 60 seconds. A request with no answer is given up on after 10 seconds, or sooner where the caller sets a shorter wait, and one still waiting when a new owner announces itself is sent again. Every message carries the protocol version. A tab that hears another version treats its sender as no owner: online, its reads go to the server, and offline the page says the app needs updating; an owner of another version is noticed only when it speaks. The lock's name does not change with the version, so two builds never open the pool together.
- **Deadlines.** An online read waits 1.5 seconds for the device. If the owner has not answered by then the tab takes it as gone, so the reads that follow go to the server at once, until the owner says it is there: the tab asks `who` and believes the reply. A read of a library that is applying, or made while the owner is `heavy`, goes to the server without asking. Where the server cannot be asked (offline, working offline, or a request that has just failed for want of an answer) the read waits for the device. If no owner is serving yet it waits up to 5 seconds, and only when the device holds the library, which an app launched offline at a deep link knows from the libraries it kept for the account in local storage while an owner served; a library not on that list is answered at once as not on this device. The timers are on an injectable clock, so the specs run them by hand.
- **One file per library.** Each library is its own SQLite file (`lib-<library>-<generation>.db`) in the `sahpool` VFS, and each file holds its own feed positions and the account's: the library feed's position, its staged pages, and the account feed's position, each with the epoch of the server's run its latest page came in, with only that library's playlists applied. A marker in the file says it is complete and belongs to the signed-in account, and a file of another account is deleted. Replacing a library's file replaces its feed positions and playlists with it. The pool is sized for the libraries plus a temporary file.
- **A first sync is a file.** A library with no copy on the device downloads the server's gzipped snapshot, as it is sent, into a plain OPFS file outside the pool, named for the library and the snapshot's ETag. The worker then inflates the file into the pool in one local loop, since the pool's import holds the whole pool, sized from the database's own header and hashing the gzip as it goes, and deletes the download. That loop cannot yield, so it holds the worker in one piece: about 1.8 s at 500,000 tracks, 6.7 s throttled, during which reads wait for it or go to the server, as during an apply. The file is published only if the hash is the snapshot's ETag and gzip's own checksum holds; a mismatch, or a gzip that will not inflate, is discarded and downloaded again. A download whose body breaks off, because the network went or the worker closed, is kept: the next try (a `hello`, or the next worker's start) asks for the rest with `Range` and `If-Range`, and appends a `206`; a `200` means the server's file changed, and the download starts over. A start keeps the downloads of libraries not yet on the device and deletes the others, and an account pull deletes those of libraries the account no longer reaches. The snapshot's response carries `X-Jewelcase-Schema` and is never kept in the browser's disk cache, and a tab whose build has another schema stops syncing that library until it reloads. The server builds the snapshot's indexes after copying the rows, which is faster than keeping them up while it fills. The new file is swapped in by generation, so nothing shows until the swap and a library is never partly there. The account feed is pulled from the start into the new file before it is swapped in, and the library feed from the snapshot's position. Before it downloads, the worker asks `HEAD /libraries/{id}/catalog` for the gzip's size (`Content-Length`) and the database's inflated size (`X-Jewelcase-Database-Size`) and compares what the download needs with the browser's storage estimate, its quota less its usage: the gzip less any part already kept, plus the database, plus 16 MiB for the journal the file keeps between transactions (`#room`). A download of another snapshot kept from an earlier try is deleted first, since the import would delete it. If the device has less, nothing is downloaded, the shortfall goes into the library's state for the account page, and the library is tried again at the next start or `hello`. The check is made again after a `503 catalog_building` wait, since a new server's first answer has no sizes; a browser with no estimate, or a server that gives no sizes, is not checked, and a full disk partway through is still reported as a quota error. A library already held that has fallen too far behind to catch up, and whose new copy would not fit, catches up through the feed instead, however long that takes. A download costs the gzip's size of temporary disk besides the new copy and its journal: about 127 MB and 360 MB at 500,000 tracks, so the check wants about 500 MB free. Libraries already on the device keep catching up while a new one downloads.
- **Catching up.** The worker pulls the library's feed and the account's on start (when online), on every realtime `hello` and on every `libraryChanged` or `accountChanged` hint. Pages of 1,000 changes are staged and committed as they arrive, so a closed tab resumes where it stopped. Each request sends the epoch the file holds for that feed with its position, and staging a page keeps the page's epoch, so a server restarted mid-catch-up is followed on and a restored one refuses the position (`410`). Once the head is reached a small catch-up is applied in one transaction. A big one is applied in slices, each its own transaction and each sized from the time the last took to hold the worker for about 50 ms (never fewer than 50 changes, since a commit costs a flush however few it holds; at 500,000 tracks a change costs 0.3 to 0.5 ms, and about 1 ms with the CPU throttled), and the worker answers between slices: a read of another library, a question of state or a pull of another feed waits for at most the slice under way. The worker's shell hands each read to the sync in turn but answers it whenever it settles, so a read that waits, for an index build or an offline apply, holds up neither other reads nor a hand-over; a read the hand-over cuts short is left unanswered, and its tab asks the next owner. The library being applied is never read part-way: pages read it from the server, and offline reads wait for the apply to finish (a page says whether it is offline with each read). A slice cannot be shorter than the disk lets it: on a btrfs disk the worst slices at 10% and 25% of 500,000 tracks take 0.6 to 0.9 s whatever their size, and a slow disk can stall a single commit for seconds (3.8 s was seen with the CPU throttled), outside what slicing bounds. An apply left part-way, because the tab closed, is finished when the worker starts, and one that fails counts as damage and is rebuilt from a snapshot, except when the device is full: then the copy stays, the error is reported, and the apply is finished on a later pull. One pull runs per feed at a time, and the worker keeps the highest position it has heard of, so a hint that arrives during a pull starts another when it ends. A catch-up that has pulled more than a tenth of a library's entities downloads the snapshot again, and never imports one at or below its own position. When the server's snapshot is not yet newer than the device's, the worker asks for it again a few times before it falls back to the feed. Each account pull re-reads the library list, so a library the account gained is downloaded and one it lost is deleted, and a hint for a library not on the list starts an account pull.
- **The device database is set up for a pool where every commit is a flush** (`Catalog::tune`, on every open, in `crates/catalog-wasm`). `locking_mode` is `EXCLUSIVE`, since one worker alone has the file open, which saves the lock traffic of each transaction. `journal_mode` is `PERSIST`, so the rollback journal is zeroed and kept rather than deleted and created again, and `journal_size_limit` is 16 MiB. `cache_size` is 32 MiB and `temp_store` is `MEMORY`, so a temporary table never spends a pool slot on a temporary file. `synchronous` stays `FULL`: `NORMAL` measured no faster here (see below) and risks a corrupt file that nothing on the device would notice. Prepared statements are cached 64 at a time. The device schema's version is 7, and every sort index ends at its sort key, with no trailing `id`: the row's own ID orders ties, serves a descending walk and a cursor's seek (`design/database.md` §4). Staged changes are a rowid table. A test reads the settings back after open, and another checks that every list's every sort, order and cursor walk is one index range with no temporary B-tree, leads excepted.
- **Reads cost what they return** (`design/database.md` §4): a tag-filtered page that walks a sort's index reads it in windows and leads from the smallest tag when the walk runs over its budget, a counted total is remembered, a page that leads from a tag or an artist sorts only IDs and keys under its `LIMIT`, and a recipe from a large tag filters the index walk against the tag's IDs in Rust.
- **An answer is written to JSON once.** The catalog builds each answer as one string, straight from the rows with no tree of values between, and the worker posts that string to the page, which parses it once (`query::answer` in `crates/catalog`).
- **A copy that cannot be trusted is replaced.** A library the account lost, sign-out, a file of another schema version, a hash that does not match, a corruption error from any query, a failed open, or storage the browser evicted (iOS does) each delete the copy and start again. A `404` from a feed does the same. A `410` downloads the snapshot again, and the old copy serves until the new one is swapped in. A snapshot of another schema version stops that library's sync until the tab reloads, keeping the copy for offline reads. Raising the device schema version also replaces files kept in an older format, such as positions without epochs. The device never runs `quick_check`: it would block the worker for tens of seconds at 500,000 tracks. Sign-out in any tab wipes the catalog for all of them. With no private file system (Safari's private windows) the worker answers nothing and pages read from the server. The page asks the browser to keep its storage and reports a full disk as a quota error. If a library the device listed for the account the last time an owner served has no file at the worker's start, for no reason the worker knows (an older schema, a file of another account and a failed start are known), the user is told once that the library is no longer on this device and will be downloaded again. A browser that clears a whole origin looks like a new device and is not reported.
- **Device data belongs to one account** (`requirements/offline.md` §9). The device wipes its catalog, kept images, queue lists, kept account details and sync log when a person logs out, when the server ends the session (a `sessionRevoked` message of any reason, or an answer `unauthenticated` or `session_revoked` to a request from a device that had an owner), and when another account signs in, which is compared with the owner the device kept, before anything of the new account is kept or connected. A server that cannot be reached wipes nothing. Where the server ended the session, the unsent plays and changes the log holds are counted first, and the login page says once how many were discarded. Like a logout, a session the server ended then reloads the page at the login page, so nothing of it, playback above all, stays in the page's memory. A visit to `/login` with a good session goes back to `/` and wipes nothing.
- **Logging out offline still logs out.** The account page first sends what the log holds if the server answers within 3 seconds, and if anything is left asks "N plays and changes haven't reached the server. Log out anyway?", deleting only on yes. It then writes a `jewelcase-logout-pending` marker, wipes the device and asks the server to end the session, waiting 3 seconds. A marker still set means the server has not been told: the app shows only `/login`, with no redirect into the app, repeats the wipe in case the page closed before it finished, and sends `POST /auth/logout` the first time it is online. A login tells the server first, then clears the marker. The session is an HttpOnly cookie, which only the server can end, so the marker is the only record of a logout made offline.
- **The caches are per account.** Kept images are in `images-<user>` and the queue's lists in `queue-lists-<user>`; the account details and the libraries held are in local storage under keys that carry the account, beside the ID of the account the device belongs to. The page tells the service worker who is signed in (`postMessage`), the service worker keeps that in its own cache, `jewelcase-signed-in`, and with no account known it caches no image. A message naming another account deletes every other account's image cache. A new service worker deletes the unscoped queue-list cache an older build made. A library the account loses has its file, images and queue lists dropped together. Every signed-in answer names its account in `X-Jewelcase-User`, and the worker checks it on each answer it acts on: one naming another account, as a session signed in elsewhere since gets, is pulled, applied and deleted on in no part, a `404` included. It never asks `GET /me` first.
- **Where a page reads from** (`catalog/read.ts`). A library not fully on the device reads from the server, and offline the page says the library is not on this device yet, never part of it. A library on the device reads from the device alone, at once, even while a catch-up is being pulled, and the catch-up's changes replace what is shown in place; only while a big apply is under way does an online read go to the server, and an offline one wait. Where the server cannot be asked, or a request has just failed for want of an answer, the read waits for the device instead. A query the device fails reads from the server when online, and a page that needs the server says so when offline. A device refuses a playlist read or a recipe whose tracks have not all arrived, instead of showing a shorter list, and the page reads it from the server. Writes are mutations of the sync log (*The sync framework*): they change the device's rows at once and reach the server in order; a playlist edit's conflict check reads the playlist from the server alone, never from the device, because a device that is behind would send a stale version.
- **Live changes.** After a commit the worker announces that the library changed, to every tab, naming the kinds of rows that changed: tracks, albums, artists, tags, playlists, liked and hidden (`kinds.ts`). The sync reads them from the feed entries it committed: a track, album, artist or tag entry names its own kind, a hidden-track entry names hidden, a playlist or playlist item names playlists and also liked where it is the account's Liked Songs, and a snapshot swapped in, or an entry of a kind it does not know, names every kind. Each list declares the kinds it depends on (`DEPENDS` in `live.svelte.ts`): a track list tracks, albums, artists, tags, hidden and liked; an album list albums, artists, tracks, tags and hidden; an artist list artists, albums, tracks, tags and hidden; a tag list tags, tracks and hidden; the list of playlists playlists, tracks and hidden; and one playlist's page playlists, tracks, albums, artists, tags, hidden and liked. So a like reloads a track list and a rename of a playlist does not. A page that shows the list reloads in place (`live.svelte.ts`), once for each burst, a second after the first announcement. A reload re-reads the loaded rows in pages of 1,000 and compares each page with the rows it replaces as it arrives (`Paged` holds them with `$state.raw`): the rows before the first page that differs keep their identity, the rest are taken as they come, and a reload that finds nothing new keeps the array itself, so a selection, a drag and the scroll position survive a scan that goes on for minutes. Every tab counts the announcements it hears for each library and kind (`changes.ts`), and a route's `load` takes the count before its first read and passes it on as `since`, so a change announced between that read and the moment the list starts listening reloads it once at once. An open playlist follows the account feed alone; the realtime `playlist` message is for third parties. A playlist edit queued or being sent from this device holds a refresh back until the server confirms it or refuses it.
- **Search** goes to the server when it is reachable and to the device when offline, when the server fails, and when the server has not answered in 1.5 seconds and the device's index of the library is already built. Without one it keeps waiting for the server: building an index online would spend the worker's time on a server that is only slow. If the device answers first the server's late answer is dropped. The worker builds the core's index from the device database in the background when the app goes offline or starts offline, for the library on screen, and otherwise the first time the device answers a search, which waits for it. It rebuilds after any change to the library's rows (the server only after a name changes), no more often than the server does (a rebuild waits ten times as long as the last one's work took), so a scan costs the worker a tenth of its time at most. A playlist edit does not stale the index. The worker keeps one index, since search covers one library at a time: building another library's lets the first go, and a rebuild lets the old index go before it starts, because WebAssembly memory never shrinks and whatever a build holds at its peak stays the worker's. The index is a few flat arrays, built from the rows as they are read, in slices of about 50 ms like an apply: reads of other libraries are answered between them, and the worker tells the page it is busy from the build's start to its end, so online reads go to the server meanwhile. The build's last step, merging the sorted runs, is in budgeted steps too, and the first slice is 2,000 documents' worth of work and each next is sized from the time the last took, up to about a million. Builds go one at a time with a pause between, so two libraries' searches each get their turn and neither build drops the other's index. A commit to the library mid-build restarts the build once the apply is over, since the rows are then of two versions. The device holds the same names the server indexes, so search says nothing about coverage; lyric search is not on the device. At 500,000 generated tracks in the browser, a build takes 0.65 to 0.7 s unthrottled and 2.6 to 3.4 s with the CPU throttled (about 4.5 times), and holds the worker for at most 76 ms at a time (192 ms throttled); a rebuild takes about 0.65 s and 2.6 to 2.8 s. The worker's WebAssembly memory, SQLite's included (its page cache is 32 MiB), is about 92 MB after three rebuilds, of which the index keeps about 27 MB.
- **Queue.** Starting or adding a recipe resolves on the device with the same SQL as the server, hashes with the core and attaches at once ([`design/queue.md`](queue.md#7-where-it-is-built-and-what-is-not-yet)). The server's snapshot names its own list, and the list is downloaded only if the hashes differ. Offline, a start gets the full list rather than the rows the view held, and lists stay in Cache Storage, kept for the account. A search recipe resolves on the device only when the app counts itself offline. A queue row for a track the device does not hold yet asks the server.
- **Measured at 500,000 tracks** (the browser's whole CPU throttled by a cgroup quota to about 4.5 times slower as a phone's stand-in; a library with a random ID, art and placeholders, built as the server builds it): the worker answers its first query about 150 ms after it starts unthrottled and 1.1 s throttled, most of it compiling the module (0.4 s) and the first query on a cold cache (0.4 s). A sorted page or a deep keyset page takes 2 to 3 ms unthrottled and under 25 ms throttled at the median, with first reads up to 28 ms and 55 ms; a tag total counted from two tags 24 to 25 ms and 93 to 100 ms at the median, its first read 105 to 107 ms throttled; and resolving and hashing a 500,000-track recipe 130 to 190 ms and 470 to 680 ms. The database is 359.7 MB, half of it sort indexes, and 126.6 MB gzipped on the wire; importing it takes 2 to 3 s unthrottled and 7 to 9 s throttled. The catch-up, slicing and `synchronous` figures below were measured on an AMD Ryzen 7 5800X desktop under Linux. Catching up feed changes costs about 0.3 ms each in the worker on a memory-backed disk, and the catch-up of 1%, 5%, 10% and 25% of the library took 3.9, 22, 60 and 119 s unthrottled on a btrfs disk, measured before the apply was sliced; throttled and sliced, 1% took 12.7 s and 5% 65.9 s. The longest time a slice held the worker at 1%, 5%, 10% and 25% was 56, 124, 573 and 791 ms on that disk, with a 99th percentile of 56.5, 59.4, 99.3 and 132.3 ms; on a memory-backed disk at 10% and 25% the median hold was 49.8 to 49.9 ms, the 99th percentile 52 to 53 and the longest 55 to 57. The tail on a disk comes from its stalls, not from the slice's size: a throttled run once stalled a single commit for 3.8 s, outside what slicing bounds, and the 99th percentile at 25% misses 100 ms unthrottled. Setting `synchronous` to `NORMAL` measured no faster than `FULL` (3,812 against 3,889 ms at 1%, 61.7 against 59.6 s at 10%), which is why it stays `FULL`. The benchmark is in `e2e/catalog-scale.bench.ts` ([`CONTRIBUTING.md`](../CONTRIBUTING.md)).

## The installable app

The app has a web manifest (`static/manifest.webmanifest`) with regular and maskable icons, standalone display, a theme colour and the iOS tags, and a SvelteKit service worker (`src/service-worker.ts`) with no extra library. The icons are a plain placeholder until the project has artwork.

- **The shell is kept per version.** The service worker downloads the build and the app's one page into `shell-<version>` when it installs, so the app opens offline, and answers navigations from it; an install whose download fails deletes that cache, so a later version never keeps an empty shell in place of the one open pages run. It takes over the page it was installed from too, so on a first visit the pages not opened yet load offline. A new version installs in the background and takes over as soon as it has installed, with no prompt and no reload of an open page: the page asks the browser to look for one at startup, when it is shown again and when the realtime connection says hello (a server upgrade restarts it), never while working offline, and the next load runs the new build. Open pages keep working, since the worker answers the build's hashed files from the previous version's shell too; it keeps that one older shell and no more, so a page left open across two upgrades must reload to load a new chunk. It is registered in production builds only, since in development it would serve a stale app, and the build writes absolute script paths (`paths.relative: false`) so the one page loads at any deep link.
- **Nothing from the API is kept except images.** What an account may see is the server's to decide on every request.
- **Images** are kept as they are seen, for the signed-in account alone, in its own Cache Storage cache (`images-<user>`) of at most 2,000 images with the oldest dropped first. The cache outlives app versions, and the account page shows its size. The service worker learns who is signed in from the page and caches nothing while it does not know; sign-out empties every account's cache. Album and artist art draws its ThumbHash placeholder until the picture loads, and when the picture is not kept and the device is offline. Placeholders decode only near the viewport, so a long list does not decode every row.
- **The last known account and library list** are kept in the browser's local storage, under keys that carry the account, so the app starts with no network, and cleared with the catalog at sign-out. Beside them are the account that owns the device and the libraries its files held when an owner last served, which an app launched offline reads before an owner has spoken. A server that cannot be reached while the network is up, or that does not answer within three seconds (waited once for the whole start, not for each read), falls back on them too. A tab with a last known account joins the catalog election as it starts, so a page opened straight onto a deep link waits briefly (up to a few seconds) for its own owner rather than answering that the library is not on this device. The account's devices, its playback state and the ID the server knows this device by are kept the same way as realtime last told them (`playback.svelte.ts`), and so are the plugins it can connect as the account page last read them, so an app started with no network shows the devices panel and the account page as one that lost its connection does.
- **Storage** is shown on the account page: whether the browser agreed to keep the device's storage (`navigator.storage.persisted()`), and for each library whether it is on the device or was not downloaded (or not downloaded again) for want of room, with the megabytes it needs and the device has.
- Downloads, and choosing between local and stream, are the next part of Stage 10 ([`PLAN.md`](../PLAN.md)).

## Connectivity

`connectivity.svelte.ts` holds where the device stands with the server as one state, which decides where every read goes: `online`, `unreachable`, `offline` or `working-offline`.

- **The states.** `working-offline` is the person's choice, kept in the browser and shared by its tabs. `offline` is the browser saying it has no network. Neither makes a request, the realtime connection included. `unreachable` is a realtime connection that was lost and stayed lost for 3 seconds or was not up within 3 seconds of starting, or an HTTP request that got no answer. It still tries HTTP, and the device's copy answers where the server fails. Any realtime message, and any HTTP answer below 500, returns to `online`; a 5xx, such as a proxy's 502, is not the server answering. A concurrent success can return the state to `online` between a read's failure and its fallback, which at worst costs the read one more try. The workers are told only whether the device is working offline; they follow `navigator.onLine` themselves and report no HTTP successes. While the browser has no network the realtime connection makes no attempt and asks no `GET /me` whether its session ended; the `online` event connects at once. With a network but no server it backs off and asks as before. The typed client sends no request while the state is `offline` or `working-offline`, and a read or a write that fails for want of an answer while the device is not online rejects as `unavailable_offline`, "Unavailable offline. This needs the server, which this device can’t reach right now.", which a page shows as its error and a form in place.
- **An indicator** shows `Working offline` or `Offline`, which covers both `offline` and `unreachable`, in the player's status label, and nothing while online. The devices panel says its list may be out of date.
- **Work offline** is a switch on the account page. It is per device: the choice is kept in the browser and shared by its tabs. Turning it on stops every request the app makes: the page's, both workers' (told, not restarted) and the images' (`gated-fetch.ts`, with art read from the cache through blob URLs), and it closes the realtime connection, pauses playback and drops the audio source. Reads are local, and the catalog worker stops pulling.
- **Surfaces that need the server** say so when offline and are not hidden: the admin and plugin pages show that they need the server, an error page says the same for any read only the server can answer, and an action only the server can carry out (logging in, setup, a scan, installing, setting up or running a plugin, connecting or disconnecting one) says "Unavailable offline" where it was asked. The account page's Connections section lists the plugins the server last offered, laid out as online; only one never read online says it needs the server. Sharing searches with one is a mutation, so it works offline.

## The sync framework

Every write the app makes, a play, a like or hide, a playlist's creation, edit or deletion, a queue's start, edit, restore or kept-queue deletion, a recent search recorded, removed or cleared, search sharing with a plugin turned on or off, goes up to the server in one way, so a feature builds on the framework and queues, retries and orders nothing itself (`requirements/general.md` §3.4 and §3.5, `requirements/offline.md` §8). Data comes back down the other way, through the change feeds (*Catalog worker*). The code is `src/lib/sync/`.

- **A mutation** is one write: its `name`, JSON `args` (ids the client mints included), a `scope`, a sequence number, an idempotency key and when it was made. The log keeps it until the server has it, so closing the app or losing power loses none of it, and the device shows its change at once, whether or not the server can be reached. Offline is the same path with a longer wait.
- **A feature declares a kind of mutation once**, as a `Definition` in `mutations/<feature>.ts` (`mutation.ts`), and the registry (`mutations/index.ts`) names it. The parts are:
  - `scope(args)`, which mutations are sent strictly in order of: the queue is one scope (`queue`), each playlist (`playlist:<id>`), each track's marks (`mark:<library>/<track>`) and the recent searches of every library with search sharing (`searches`, so a plugin hears only searches made while sharing was on) are one, and so are plays (`plays`). Scopes are sent side by side, so a playlist the server will not take never holds up the plays.
  - `send(args, { fetch, key })`, the request, sent with `Idempotency-Key: key`. What it resolves with is the answer: the next mutation of the scope is handed it as `carried` (a playlist edit's version), and whoever waits for this one hears it.
  - `apply(args)`, optional, the writes the mutation makes to the device's catalog, named as the shared Rust code (`crates/catalog/src/mutate.rs`) takes them. A mutation of no catalog data leaves it out; the queue's change is made by the queue's own core instead.
  - `merge(pending, next)`, optional, which folds a new mutation into an unsent one of the same scope: a track's latest like and hide state, or a play's latest listen time. The merged one is sent under a fresh key.
  - `batch`, optional, how many unsent mutations of a scope one request may carry: plays go 500 at a time, and a batch the server refuses is sent again in halves to find the play it refuses.
  - `confirmed(args, answer)`, optional, what a write's answer says it left (a playlist and its version), which the device checks itself against once the write has left the log (*Local apply*, below).
  - `silent`, for a kind whose feature tells the user itself when the server refuses it (the queue's, through the queue panel), or that need not be told at all (a recent search, only a convenience lost), and `refused(args, code)`, what to say for a refusal's code instead of "Couldn’t …"; `what(args)` finishes "Couldn’t …".
  - `depends(later, refused, name)`, optional, whether a later mutation of the scope was made on the one refused, so it goes with it. None does unless this says so: a playlist's edits all depend on each other, and a queue's edits on the start or restore that made their queue active.
  - A mutation may be logged with `notBefore`, a time before which it is held, and an unsent one may be cancelled (`Sender.cancel`), which takes its change back off the device. `Sender.hold` moves the time. A playlist's deletion is held for as long as its Undo toast is open plus a second, so Undo cancels it, which survives a closed tab since the log holds it.
- **The sender** (`sender.ts`) sends the log, one for each page, by these rules:
  - Within a scope, one at a time in order, each given what the answer before it carried; scopes in parallel.
  - Nothing is tried while `connectivity.blocked`: no network, or Work offline. It is woken at once by `online`, Work offline turning off, the realtime `hello`, the page becoming visible and the app starting, and each time something is logged.
  - **What follows a failure.**

    | Answer | Action |
    |---|---|
    | 2xx | delete from the log |
    | 401, or a redirect to log in | halt and keep everything until the next wake; where the session had been good, it has ended, so the device is wiped, the log with it, and the login page tells how many were discarded |
    | 403, 404, 413, 422 and any other refusal | drop it and the later mutations that depend on it, take their changes back off the device and tell the user once, in the definition's words |
    | 408, 429, 5xx, no answer | wait and try again: 1 second doubling to 30, spread at random between half and the whole, or as long as `Retry-After` says |

    A request that gets no answer, one made after the device went offline, and a proxy's gateway answer (502, 503 or 504) for a server behind it that is down do not count as failures, so a server that is down for hours costs a mutation nothing, and only its age sets it aside: over 7 days when a try fails. The age is checked only then, so a mutation kept offline for longer is still sent when the server can be reached. Any other 5xx counts. After 20 answered failures or 7 days a mutation goes to the `dead` store, with those that depend on it, each with when and why (`SetAside`), the user is told, the device takes back their changes, and the sender carries on.
  - **What was set aside is recoverable** (`requirements/offline.md` §8). The account page lists it, what each was and when it was made and why it was set aside, with those made on it counted under it, and offers **Retry** and **Discard** for each (`Sender.setAside`, `retry`, `discard`), but only Discard for a change to the queue: sent days late, a start or restore would make that queue the playing one on every device, and an edit is refused once another queue is active. Retry puts it back in the log with those made on it, after everything the log holds, with fresh tries and its age counted again from then (`since`), under its first idempotency key so a write that had applied is not applied twice; the device makes their changes again and they are sent. Discard lets go of them; their changes were taken off the device as they were set aside, and the device is rebased again to be sure. Either works offline. The count of what was set aside is part of the unsent count a logout asks about and a session that ended reports.
  - **Written before it is sent.** A mutation is written to the database, then sent, and the write of a user's action asks IndexedDB for `durability: 'strict'`, so it has reached the disk when the call settles; actions are infrequent enough that a flush each is cheap. A retry's bookkeeping is not strict. Everything is held in memory as well, and a write that fails is told once ("This browser couldn't keep your changes for later…") and the mutation is sent anyway. Every database call is given 2 seconds, a connection that was closed under a call or broke (`UnknownError`, `InvalidStateError`) is opened again once, and every connection closes when another asks to change or delete the database.
  - **Ownership and adoption.** Each mutation belongs to the tab instance that logged it, which holds the Web Lock `jewelcase-tab-<instance>` while it lives. A tab sends its own mutations at once and takes no lock to do so. Those whose owner's lock is free, which a closed tab leaves behind, are adopted: one tab at a time looks for them under the lock `jewelcase-outbox-<user>`, taken only if free (a tab that finds it taken tries again after 2 seconds), and each is claimed by a transaction that changes its owner only if the old owner is still the one named, so only one tab wins it. The lock guards the looking and nothing else, so a click followed at once by a navigation is never held back by it. A tab adopts before it sends anything of its own after a wake, so a scope reaches the server in order across tabs. A resend after a lost claim is harmless: every mutation is idempotent under its key.
  - **The epoch.** The sender counts the times it lets go of a log (a new user, a stop, a wipe), and a request or write that outlives its log does nothing to the next user's, so nothing crosses accounts.
  - **The wipe.** A wipe tells every tab over a `BroadcastChannel` named for the database to close its connection and write no more, then deletes the database; a deletion a tab still blocks is announced again, and after 2 seconds is left queued behind the connection that blocks it. The queue's worker stops too, and a connection that is told the database is deleted never opens it again, so a late write cannot make it anew.
- **Local apply, rewind and replay.** A mutation's `apply` runs in the catalog worker of whichever tab owns the device's copy (`device.ts`, `catalog/sync.ts`), through the same Rust the server's handlers call for the rows a device keeps (`crates/catalog/src/mutate.rs`, `crates/catalog-wasm/src/mutate.rs`), so a device and the server change the rows the same way. Each write is made at the time the mutation was made, so making it again changes the same rows, and is named by a call ID, so making it twice is making it once.
  - **The undo is in the file.** The write's undo, the rows it touched before it, is kept in the library's own file (`mutation_undo`), committed in the same transaction as the write, so a crash can neither leave a write that cannot be taken back nor take one back twice. A snapshot starts without any.
  - **Rewind, feed, replay.** Before the worker applies a page of the account's feed that holds changes, it takes back every write the file holds, newest first. It applies the feed, then makes again, in the order they were made, those writes whose mutations are still in the log (`#rewind`, `#replay`), in slices of about 50 ms, each one transaction with a savepoint per write (`applyCalls`), so a write refused on replay is that write's alone and a long log costs a few commits, not one each. A write the server has answered is gone from the log, so the feed's own rows stand and nothing doubles; one not yet answered stays shown over the server's newer rows. A write the device refuses on replay, such as an edit made on a version the feed has replaced, is not shown, and the server's answer decides it. A write answered after a feed page was fetched but before it was applied shows again until the next pull, which the server's `accountChanged` hint brings at once.
  - **An answered write stays until the feed brings it.** The sender tells the device of each write the server answered as it leaves the log, and the file marks it answered. One the file lacks, which a rebase under way took back, is left to the feed, as it may already have brought it: made again then, it could stand over the feed's rows with nothing left to take it back. Every other rebase (after a refusal or a cancel, or as a worker starts) keeps an answered write, with what made it, and makes it again before the log's, so nothing the user did vanishes while no feed comes, as offline for days. Only the rewind before an account feed's apply drops them, as that feed brings them, and the check of an answered append (`confirmed`), which finds the feed brought it. A library's own feed is applied with no rewind or replay: the writes' undos hold account rows only and a deleted track does not cascade into them.
  - **Refusals.** When a mutation is refused or cancelled, the sender asks the worker to take back every write of the library and make again those the log still holds (`rebase`). An append whose rows the feed brought before its answer reached the sender is told the version that answer named once it has left the log (`confirmed`), and the library is rebased if the copy is already past it, so it shows once.
  - **Announcements.** The worker tells pages what each apply changed by kind of row, so lists reload in place; for its own writes, the kinds of the rows the shared code reports it wrote (its `Effect`s). The sender tells whoever waits for a mutation what became of it (`settled`: `sent`, `dropped` or `cancelled`, with the answer, or the problem code and what the user was told) and its listeners (`onSettled`), once the log has let go of it, and toasts once for a refusal unless the definition is `silent`; one set aside is always told.
  - **Where the library is not on the device.** The writes are made when it is (the replay does it). Until then two overlays show a write at once: `marks.svelte.ts` for likes and hides, and the playlists' `deleted` set. They are the only display of a write for such a library, and not a second source of truth for one on the device.
- **The queue in the log** (`design/queue.md` §7). The queue worker applies a start, edit or restore, and a kept queue's deletion, at once, with the core and the kept queues it holds, and posts the mutation to the page (`enqueue`), whose sender logs and sends it as the `queue` scope; the page tells the worker what became of each (`settled`), with the server's answer. The worker does no sending of its own, and reads the queue from the server only once nothing it gave the log is unsent. It keeps one record in the database's `queue` store, the queue the server last confirmed, and when the app opens it shows that with the log's unsent mutations on top, in the order they were made, whichever tab made them (*Queue worker*, below). The mutations' definitions are `mutations/queue.ts`.
- **The database** is `jewelcase-outbox-<user>` in IndexedDB, behind a small port (`store.ts`): IndexedDB in browsers, memory in node specs and where the browser has no IndexedDB or Web Locks, which keeps nothing past the page. **The name is that of the first version's database, which held only an outbox, and stays: a new name would strand what version 2 held unsent.** Its stores are `mutations`, the log; `dead`, the mutations set aside; `queue`, the confirmed queue; and `kept`, the account's kept queues with their states (version 4), each keyed by `key`. Every record carries a revision that changes with each write, so a delete can leave a newer write in place; the tab instance that owns it; when it was made; and how many answered failures it has had. A store is added by raising the database's version, which `onupgradeneeded` creates without touching the others. The upgrade from version 2 to 3, inside its one transaction (`migrate.ts`), turns every play, each track's latest mark and each unconfirmed edit of a playlist chain that version 2's `plays`, `marks` and `playlists` lanes held into a mutation of the log, keeping an edit's own idempotency key so one that had applied is not applied twice, turns what version 2 set aside in `dead` into mutations set aside the same way, so they can be retried or discarded, and deletes the lanes. Version 2's queue records, each tab's unsent start and edits, are not moved: they were made on a queue of another shape and cannot be replayed safely, so a queue started or changed offline and not sent before the upgrade is lost. Only browsers that ran the unreleased version 2 hold any.
- **The server** carries out every signed-in write once for an account and `Idempotency-Key`, and sends the stored answer, kept 8 days (a day longer than the log's 7), to a repeat however late (`crates/server/src/api/idempotency.rs`, `design/database.md` §6). The answer is stored by a write of its own after the handler's, so a crash between them lets a retry meet the handler's own checks (a playlist's version or taken id). A queue edit's `editId` is its key when the request sends none. The client mints the ids it needs so the page can open what it made before the server answers: `createPlaylist` and `recordRecentSearch` take a positive 63-bit `id` (`409 id_taken` if used), so a removal names the same search on the device and the server whether or not its record has been sent, a like may carry the `likedId` Liked Songs is created with, and `playId` and a queue's `queueId` are minted already. Every signed-in answer names its account in `X-Jewelcase-User`.
- **What a page shows.** A page reads the device's rows, which already hold what is pending, so a like made offline still shows liked after a reload and a playlist's page shows its pending edits, whoever made them. A playlist page whose library is on the device reads the device alone, and a new playlist opens at its own address at once; where the library is not on the device, creating one online waits for the server's answer and offline is logged with a note that it will be created on reconnect. The search box offers the device's recent searches, online and offline, and records, removes and clears them through the log (`mutations/searches.ts`); only a library not on the device is read from the server. The device lists them without the server's 30-day window, which it has no clock for in its shared read: those aged out leave it when the feed's tombstones arrive.
- **Plays are checkpointed.** The play under way is logged whenever the page becomes hidden and every 30 seconds while it plays, each time in full under its own ID, which merges into the one before, and the server keeps the largest listen time, so a page closed without warning loses at most the last 30 seconds. When the page closes, the play's end is also sent by a request that outlives it.
- **Logging out with unsent work** sends what it can, and if mutations remain, asks before deleting them (*Device data belongs to one account*, above). Those the server ended the session with are counted before the wipe and the login page tells how many were discarded.
- **To add a mutation:** declare a `Definition` in `mutations/<feature>.ts` (`scope`, `send`, `what`, and `apply`, `merge`, `batch`, `depends`, `silent` or `refused` only where the feature needs them), add it to the registry, and call `sender.enqueue(name, args)` where the action is made. Never reuse a name for other arguments: a log written by an older build is sent by a newer one. A write the device must show needs a write in `crates/catalog/src/mutate.rs` for the server's handler and the device to share.

## Queue worker

`src/lib/queue/` holds the account's queue in a web worker, so loading and editing a queue of any
size stays off the page's thread (`design/general.md` §7.1). `worker.ts` is a shell around
`QueueStore` (`store.ts`, plain TypeScript, so it also runs in tests); `client.svelte.ts` is the
page's side, and `protocol.ts` is what they say. The store runs the shared core, built to
WebAssembly by `pnpm wasm`, and holds no rule about the queue's order. Its state holds no tracks:
the core knows each source's length and, once attached, its list, which the store fills in from
the server (*Lists and rows* below, `design/queue.md` §3).

- **Snapshot.** On every realtime `hello` the store fetches `GET /me/queue`, naming the `ETag` it
  holds, `"<run>.<queueId>.<version>"`. The server answers `304` when nothing changed, so a
  reconnect downloads and rebuilds nothing, and the page hears nothing. Otherwise the state loads
  into the core with `Queue.fromJson`. `404` is no queue.
- **Two queues.** The *confirmed* queue is the snapshot with every `queueEdit` applied in version
  order. The *view*, which the page shows, is a `copy()` of it with this device's *pending* edits
  replayed on top, so the copy shares attached lists. With nothing pending the view is the
  confirmed queue itself.
- **Edits.** `edit()` applies at once to the view, then hands it to the page's sync log as a mutation
  (*The sync framework*), which sends it in order with the rest of the `queue` scope. Each carries a device-minted
  `editId`, its idempotency key, resent unchanged if the answer is lost, so the server applies it once. The edit
  carries no base version. A `queueEdit` one past the confirmed version applies to it; if it is
  ours, by `editId`, the pending edit is done, so it is never applied twice. A gap, another
  queue's edit or an edit the core refuses means the copy cannot be trusted, and the queue is
  fetched again.
- **Edits that do not stay.** The store reports each, with a `Refusal` carrying the code and the
  edit, to the page (`client.refusal`, shown as *The queue panel* says): the core refused it here
  (`anchor_gone`, `invalid`); the server refused it (`anchor_gone`, `play_gone`, 422 and the
  like), and the view is rebuilt without it; a `queueEdit` heard first took what a pending edit
  needed (the core's code on the replay); the server had another queue active by the time it
  arrived (`superseded`, from its `queue_changed`, or a fetched queue that is not its own); or the server
  answered it but, after a restart, no longer has it (`lost`), which is told by its version
  being past the snapshot's. A lost edit is not sent again, since that could apply it twice.
- **An `add` of a `recipe`,** such as an album, applies at once as the number of rows its view
  counts (`edit(edit, length)`), which are `unknown` until the server's list or pages say what
  they are. Its `queueEdit` carries the source as the server registered it, with the length it
  resolved, and replaces the pending add. One sent with no length shows only when that arrives.
- **`queueReplaced`** for a queue other than the one held fetches the new queue, once the
  worker's own mutations are settled. `queuesChanged` reads the kept queues again (*Kept queues*, below).
- **Lists.** The store downloads each list the confirmed queue references, `GET
  /me/queue/lists/{hash}`, one at a time in the background, those the item playing and Up Next's
  first 100 rows read first. A list is kept by hash in Cache Storage (`lists.ts`, cache
  `queue-lists-<user>`, not the HTTP cache, which iOS evicts quickly) and attached to the core
  when it arrives. A fetch installs a fresh core queue that holds no list, so `#install` shares
  the lists the confirmed queue holds with it (`adoptLists`, which parses nothing), reads only the
  others from storage before the queue is swapped in, and downloads only those it still lacks. When a
  change leaves the queue no longer referencing a hash, as clean-up drops a source, the list is
  released: deleted from storage. Loading a snapshot also deletes every stored list it does not
  reference. A `404` marks the list `gone` for as long as the queue references it; a failed
  request, `failed`, is tried again on the next `hello`. Where Cache Storage is missing or throws,
  as in a private window, lists stay in memory instead and pages cover the gap. Every Cache
  Storage call is bounded by a 2 s timeout; past it Cache Storage is given up for the session, so
  a cache that never answers cannot stall the queue.
- **Own adds.** An add of `tracks` shows its tracks at once: with no list and no page for a row,
  `rows()` reads the pending add's `tracks` by the row's source and position, which is right
  through a copy or the shuffle, since the server's list is those tracks. It needs no hash. When
  the `queueEdit` names the `list`, the tracks are kept under that hash and attached to the
  confirmed queue, so they are never downloaded back and no page is fetched.
- **Rows.** `rows()` (the `rows` message, `QueueClient.rows`) answers a window of `current`, `upNext`
  or `history` with each row's `item`, `libraryId` and `track`, filled from the attached list,
  else from a page (`rows.ts`), else from a pending add's own tracks, else not at all. A row without a track is `unknown` while its
  list is on its way or not yet confirmed, and `unavailable` when its list is `gone`, when it is
  `failed` and no page that holds the row is being fetched, or when a page says the server cannot
  read it, so the player can skip it in place. Pages,
  `GET /me/queue/rows`, are fetched for the first 100 rows of Up Next and of History and the item
  playing as soon as any lacks a track, and for a requested window; they fill by item, so any
  version's is right. A page is asked for again only when the confirmed version changes (or on
  `hello`), so a window asked for again whenever `revision` changes never loops. What a page gave
  for a source is dropped once its list is attached. No edit waits for a list or a page. The last
  fill of §3, the rows of the view a start came from, is *Starts* below.
- **Starts.** `start()` (the `start` message, `QueueClient.start`) makes the queue the new one at
  once, as a start from a view does: the state is the core's own start (`Queue.started`), the
  source as long as the view's `total` (or its `tracks`), no list, the clicked row current and
  the cursor after it, and the repeat mode shown, which the server's start copies from the active
  queue once any repeat change not yet sent reaches it. The start is a mutation of the log's
  `queue` scope (`design/queue.md` §7): the old queue's unsent edits are sent before it, and the
  edits made after it, which name the new `queueId`, after it. A start of `tracks` is answered with `{list, length}`: the tracks are attached under
  that hash and kept, so nothing is downloaded back. A start of a `recipe` then fetches the
  snapshot, with no `If-None-Match`, since the server's list and start may differ from the view's.
  A fetch that began before a start, or whose install was waiting on stored lists, is never
  installed over it. If the server's list is not as long as the view's, or its snapshot makes
  another item current, the view's rows are dropped, so the row waits for a page. A start the server refuses (4xx)
  is taken back with the edits made on it, which the log drops unsent; the failure is reported
  with no edit, and the server's queue is fetched.
- **The view's rows.** A recipe start holds the rows its view loaded, by position. While the
  queue is unshuffled, or for the item playing, they fill the rows read straight from the source,
  after the list and a page, so a page the server gives replaces them if the library changed.
  They are dropped once the list is attached or clean-up drops the source. A row nothing can fill
  is `unknown`, however the server answers: its list is on its way, after a confirmed start in
  the snapshot that follows and after an add of this device's own in the add's answer, so the
  player waits for it rather than skip it.
- **Kept queues.** The worker keeps the account's kept queues in the database's `kept` store, one record each: the entry the Kept tab shows (`KeptQueue`), and the state a restore installs, with its version, context and where playback was left. On `hello` and `queuesChanged` it reads every page of `GET /me/queues` and makes that list the device's; the first page names the `ETag` of the list last read whole, and a `304` takes that list again, so an unchanged list costs one answer with no body: an entry that agrees with the one held stays as it is, one the server no longer lists goes (deleted, restored elsewhere or expired), and so does one inactive for 30 days when the app opens. Then it fetches, one at a time in the background, the state of each entry it holds no state for at that `lastActive` (`GET /me/queues/{queueId}`), keeping the state before it looks for the lists it lacks, so an install meanwhile does not let go of them, and counting it had only once every list is there; the page is told only when an entry changes, never for a state. The lists stay in Cache Storage beside the queue's and are let go of only once no kept queue or the queue shown references them. A start or restore made here keeps the queue it replaces at once if it was adjusted, as the server does: its view, so the edits made on it, with the lists only this device holds (a pending add's tracks, a start not yet answered) attached under the hash the server gives the same tracks (`listHash`), and where the player was (`parked`). Such an entry is kept while the mutation that parked it is unsent, whatever the server lists; once that mutation is settled the list is read again, and the server's entry and state replace it. A deletion leaves the list at once, and a read of the list leaves out a queue whose deletion or restore is unsent. The page holds the list as `QueueClient.kept`.
- **Kept for the next time the app opens.** The worker keeps the queue the server confirmed as the account's one record in the database's `queue` store, and shows it with the log's unsent starts and edits on top when the app opens, so a queue edited or started offline reopens offline as it was left; the page's sender sends them when the connection returns (*The queue survives closing the app offline*, `design/queue.md` §7).
- **Connection.** `connect()` spawns the worker and passes it `hello`, `queueEdit` and
  `queueReplaced`, gives the page's sender the mutations the worker posts (`enqueue`), and tells
  the worker what became of them (`settled`). The worker's own reads are not tried again on a
  timer: a fetch of the queue that fails waits for the server to be heard from.

## Player

`player.svelte.ts` plays the queue's current item through one audio element, and moves through
the queue only by editing it (`requirements/queue.md`, `design/queue.md` §3).

- **A start from a view** (`play(tracks, index, context, from?)`) plays the clicked track, whose
  summary the view holds, before anything is answered, and starts the queue in the background. The
  item is `<key>.<index>`, which the report names. With `from`, a recipe and the view's `total`
  (`PlayFrom`), the request carries the recipe, `start`, `startTrackId`, `total` and the loaded
  rows; without it, the tracks. Album, artist, songs, search and playlist views send a recipe,
  carrying the view's tag filter as `filters` (`tagAll`, `tagAny`) so the server resolves the
  rows shown; a sorted search sends tracks, since no recipe gives its order. A playlist's recipe
  is `{type: 'playlist', playlistId}` with the page's `sort` and `order` together, named as
  `listTracks` names them and date added as `addedToPlaylist` (D41), or neither for the
  playlist's own order (D40); the server resolves the stored
  playlist with the core's comparator, so it equals the rows shown, and never takes a `version`
  from the device. A playlist card sends the bare recipe and queues by the summary's `trackCount`
  without fetching its items. The
  recipe's filter is the one the rows were loaded under (`data.filter`), or on an album and a playlist, which
  filter their own tracks, the filter shown. An album or playlist whose `tagAny` tag has no known type (not
  carried by its tracks, not yet read) would group it differently from the server, so it sends
  the tracks shown until the type is read; so does a playlist with edits not yet confirmed, which
  the server would resolve as last saved. So does a playlist sorted by date added once songs were
  added on the page, an undo's included: the server dates them by its own clock as it saves them,
  and the page keeps this device's dates. A Next pressed before the
  worker has the queue is carried out once it has.
- **Following.** A device holding playback plays whatever the queue's current item becomes,
  whoever moved it. The item's row is read from the worker. `unknown`, a row still being learned,
  waits, and the player looks again with each change to the queue. `unavailable`, or a track
  that is missing, out of reach (403, 404) or fails as media, is skipped in place: one more
  `next`, or `previous` when going back, applied at once. Going back past History's start goes on
  forward. A failure to reach the server (a network error, 5xx, 429) is never a reason to skip:
  the player waits paused and asks again every 3 seconds. A run of skips stops when it
  comes round to an item it already passed over (reset when audio plays): playback stops and says
  that nothing in the queue can play, under Repeat All too. A pause cancels a track waiting to be
  asked for again. If the server's queue makes the track just started
  another item, the same track goes on under the new item. A start the server refuses leaves the
  player paused on the chosen track with the refusal shown, while the old queue comes back.
- **Controls.** Next and a track's end send `next`; Previous restarts a track played more than 3
  seconds, or with an empty History, and otherwise sends `previous` with a fresh key; Repeat One
  plays the item again here, and Repeat All is the queue's own. `jump(item)`, shuffle (with a
  device-chosen `u32` seed) and repeat are edits too. The next row's track is fetched ahead.
- **Reports** name only the `itemId`, which the server refuses unless the account's active queue
  holds it. So a report waits until the server has the item: a start's takeover for the start's
  answer, a Previous's copy for its edit's confirmation (the queue worker says which item the
  server's queue has playing). A report the server refused is sent again when the queue next
  changes, once per change. A play records the queue's context. Its `context` and `origin` are the device's, as sent (the server cannot tell the Manual Queue from the context for a play reported after the queue changed), and the web records `manual` for a play of an item from the Manual Queue (the worker's
  `playingManual`, from the core), `context` otherwise.
- **Restores.** `restore()` (the `restore` message, `QueueClient.restore`) installs the kept
  queue's state the worker holds at once, online or not, as a fetch's is (stored lists attached),
  keeping the queue it replaces if it was adjusted, and logs `POST /me/queues/{id}/restore` in the
  `queue` scope, after what was made before it and before the edits made on it; its
  `Idempotency-Key` makes a resend harmless. A state not yet on the device is fetched first, after
  the list if the queue is not in it, unless the app counts itself offline, which answers
  `offline`; one that cannot be had answers `unreachable`, and one the server no longer keeps
  `not_found`. It answers `position`, where playback was left. The item playing is not `held`, so
  nothing is reported, until the server answers: then the queue is fetched once the edits made on
  it are settled, which answers `304` when the device's copy is the server's. A restore the server
  refuses is taken back with the edits made on it, as a refused start is, the server's queue is
  fetched and the refusal is shown once. A restore the log still holds as the app opens is
  installed again from the kept state.
- **Taking over** a track another device plays needs the state's `itemId` to be the queue's
  current item, with its row known: playback moves without rebuilding the queue. It fails, and
  starts nothing, while the queue here is not that far or the item is of another library.

## The queue panel

Opened from the player bar, over the main area like Lyrics and Devices. It shows and edits the
account's queue, so it works the same whichever device plays: every edit goes through the queue
client, applied here at once and sent on, and the device holding playback follows the queue. It
has three tabs, Up Next, History and Kept, an accessible tab list (arrows, Home and End move between the
tabs, and the selected tab's panel is labelled by it); each tab draws its own list, so nothing but
the tab's name carries from one to the other.

- **Up Next** is the Manual Queue under its own heading (a hint stands in when it is empty), then
  the context's items under theirs. **Shuffle and Repeat** (Off, All, One) sit beside the heading,
  since the player bar hides them at phone width; they go through the player (`setShuffle`,
  `setRepeat`), so a shuffle sends a random 32-bit seed.
- **Rows are one fixed height, so the list is virtualized by arithmetic** (`queue/layout.ts`,
  `QueueList.svelte`): the rows to draw come from the scroll position, and the worker is asked for
  those rows only (`rows('upNext', offset, limit)`, the Manual Queue's first). Each is drawn as
  soon as the worker names its item, and shows its track once the batch lookup by IDs has it
  (`queue/summaries.ts`, at most 100 IDs per library per request, never none). A `loading` row is
  one the worker is still learning (it is asked again when the queue changes); an `unavailable`
  one, or a track out of reach or missing, shows "Unavailable". A 500,000-item Up Next draws about
  twenty rows. The list is drawn at most 10 million pixels tall, since Firefox ignores a taller
  height, and past that the scroll position is scaled into the whole list.
- **Editing.** A grab handle drags one row, or the selected rows together, anywhere in Up Next,
  across the Manual Queue's end too (`move`, with an anchor from `anchorAt`); the handle takes no
  scroll from a finger, and pressing it without moving selects the row. From the keyboard, Space on
  a title selects, Alt+↑/↓ moves the selection (or the row) a place, Delete removes. A row's ✕
  removes it, or the selection it is in. Presses made before the list has caught up with the last
  edit wait for it, so holding a key moves one place per press. Clicking a row jumps to it
  (`player.jump`), and everything ahead of it goes to History.
- **History** is the same virtualized list, newest first, read as `rows('history', offset, limit)`
  (each row carries its play number) and shown through the same by-IDs lookup. A row is named
  `<play>:<item>`, since Repeat All can play an item more than once, and every History edit names
  `{play, item}`. Clicking a title, or Enter on it, goes back to that play (`player.rewind`, a
  `rewind` edit with a key minted here, the device taking playback as for a jump); the ✕, or
  Delete, removes it (`removePlays`); the plus puts it at the front of Up Next (`requeue`, with its
  own key) and takes it out of History. Rows do not move, so where Up Next has its grab handle
  History has a check button that selects, and Space on a title selects too; the ✕ removes the
  whole selection. A row that is still being learned or cannot be read cannot be rewound to or
  re-queued, and can be removed. An empty History says nothing has played.
- **Kept** is the third tab, so kept queues (`requirements/queue.md` §6) are reached the same way
  at every width, by touch, mouse and keyboard, beside the queue they were once the active one of
  (`KeptQueues.svelte`). The list is the device's (`QueueClient.kept`, *Kept queues* above), drawn
  50 entries at a time with a Show more button. Each entry names the
  song it was playing (the by-IDs lookup), its context (an album, artist or playlist by name,
  looked up in the library of the song; otherwise by kind), its Up Next and History counts and
  when it was last active. Pressing the entry restores it (`player.restore`): the queue worker
  installs the state it holds at once (`#starting` keeps the queue playing from being followed
  meanwhile), then the player takes playback over here as a start does, plays the current item
  from `position` (`#resumeAt`, used when the item loads) and reports it as a start once the
  server has answered the restore. The panel then shows Up Next. The trash button deletes with one press, and
  `queue_active` is explained: the active queue is replaced by a start. A failed restore is
  shown and nothing changes. The list and a restore work the same offline (`design/queue.md` §7).
- **Adding to the queue** (`queueing.svelte.ts`). Every ⋯ menu (song rows and the selection bar,
  album, artist and playlist cards and detail headers, the Songs page and the search Songs
  header) opens Queue next, Queue last and Add to Up Next…, above Add to playlist (which a view
  with no entity, such as all songs, lacks). They are an `add` at `manualStart` / `manualEnd`, or
  at a point chosen in Up Next, and a toast says what was done at once. **What goes as a recipe:**
  album, artist and playlist pages and cards (in the order shown), the Songs page, and an
  unsorted search's songs, each under the view's tag filter; the device holds no tracks for these, so the add shows at once as the view's count of
  rows, which wait for the server's list or pages. **What goes as `tracks`:** individual song rows, selections and sorted search rows; these show at once from the tracks sent. **Dropping at
  a point:** with a mouse (`pointer: fine`) song rows, the selection and cards drag from a view
  onto Up Next, which draws the drop line and scrolls near its edges; the gap becomes an anchor
  with `anchorAt`. Touch and keyboard use **choose where**: Add to Up Next… opens the panel on Up
  Next with a bar (Add to the end, Cancel), an Add-here button and the title of each row, and
  Add first / Add last on the Manual Queue's headings; Escape or Cancel gives it up, and closing
  the panel clears it. **With no queue** these say "Start something playing first, then queue
  more." and send nothing, since the core has no empty queue to add to (D25).
- **A change that did not stay is explained** in the panel from the client's `refusal` (`anchor_gone`,
  `play_gone`, `superseded`, `lost`, ...), until dismissed. A rewind to a play another device
  removed first (`play_gone`) is dropped from the view, as every refused edit is, and the panel
  says that song is no longer in History.

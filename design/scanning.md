# Scanning Design

## Overview
How music on disk becomes rows in the index and, later, analysis results. This file turns [`requirements/scanning.md`](../requirements/scanning.md) into a pipeline, a crate, and a set of library choices, within the goals of [`requirements/performance.md` §5](../requirements/performance.md#5-scanning--analysis). It builds on [`general.md`](general.md); where it conflicts with [`requirements/`](../requirements/), the requirements win.

The one thing this design exists to get right: **incremental cost is proportional to change, and nothing that touches audio samples runs on the indexing path.**

---

## 1. Placement

```
crates/
├── core/        # Format, sort keys, name folding, search — pure
├── ffmpeg/      # subprocess wrapper: probe, decode, resize, transcode; background pool
├── scanner/     # this design
└── server/      # SQLite store, admin API, wires the three together
```

- **The scanner is its own crate, not part of the core.** The core is pure by rule ([`general.md` §3](general.md#3-shared-core)); scanning is nothing but I/O. The scanner uses three things from the core: sort keys, so a track's sort position is fixed at scan time and never recomputed by a client; name keys, to drop repeated values of a multi-value tag; and `Format`. The server's store, not the scanner, calls the core's name folding when it finds or creates artists, albums, and tags.
- **Its types and ingestion rules live in the scanner.** `TagSet`, `AudioProperties`, multi-value splitting, and LRC parsing are ingestion rules: the server stores and serves their results, and no device reads a tag or parses LRC. `Format` lives in the core, since ffmpeg checks its decoders against the same list.
- **Persistence is a set of traits the server implements.** A scan speaks to a `Store` with a handful of batch operations (upsert tracks, mark missing, record problems, append feed entries) and never opens SQLite itself. Analysis and placeholders each speak to a narrower trait of their own, their queue and its results, with somewhere to record the problems they find. This keeps SQLite specifics in one crate. The server's store is the only real one, so the scanner's pipeline tests run in the server against it ([§15](#15-verification)); the scanner's own tests that need a store but no index, those of the queue, the watcher and the workers, use one that keeps scan rows and indexes nothing.
- **ffmpeg is a separate crate because two consumers need it.** Analysis decodes with it; playback transcodes with it ([`requirements/playback.md` §1](../requirements/playback.md#1-delivery)). One crate puts the same input guards on every invocation ([§11](#11-ffmpeg)) and keeps the two kinds of work apart: background work runs in its pool, where a watchdog kills a child that stalls, and interactive work runs outside it, under its caller's own bound ([§10](#10-priority-and-pacing)).

## 2. The Pipeline

Every file that reaches the scanner passes through the same stages, and every stage yields one `FileOutcome`: unchanged, returned from missing, added, updated, kept though unreadable, or a problem ([§6](#6-track-identity) adds moved once track identity is built). Stages are ordinary functions over that type; the scan loop is a fold.

| Stage | Reads | Produces | Cost per file |
|---|---|---|---|
| 1. Discover | directory entries | candidate paths + `stat` | one `readdir` per directory |
| 2. Skip | index row | unchanged, or continue | a share of one index read per directory |
| 3. Read | file header and tag regions | `TagSet`, `AudioProperties` | tens of kilobytes of I/O |
| 4. Identify | stage 2's index row (deferred, [§6](#6-track-identity)) | new / updated | — |
| 5. Sidecars | directory cache | artwork, artist image, biography, lyrics refs | amortized to per-directory |
| 6. Persist | — | store batch + feed entries | amortized to per-batch |
| 7. Reconcile | listing against stage 2's read | missing marks | nothing more |
| 8. Analyze | whole file, via ffmpeg | loudness, waveform | **never on this path** |

- **Stage 2 is the whole incremental story.** Path, size, mtime, and sidecar stamp unchanged means the file is done without being opened. The stamp hashes the path, size, and mtime of each sidecar the file resolves: its cover, artist image, and biography after the upward walk, and its lyrics file ([§5](#5-sidecars)). It is taken from the listings discovery already holds, which carry each file's size and mtime, so it adds no I/O beyond listing each folder above a folder-scoped scan's, as discovery would, and stat'ing the sidecars there. Each directory's cover, artist image, and biography are hashed once into a digest, which is the stamp of every track in it without a lyrics file, so only a track with one costs a hash. A sidecar added, replaced, or removed therefore re-reads each track that resolves it and no other, since one a nearer sidecar overrides is not in the stamp, and an empty lyrics file, which is no lyrics, stamps as none. Each directory's index rows come in one read, which reconcile uses too ([§8](#8-reconciliation-and-missing-files)). Ten changed files cost ten opens; the other 499,990 cost one `stat` each and a share of their directory's read, and write nothing. A failure here is the failure mode [`requirements/performance.md` §5](../requirements/performance.md#5-scanning--analysis) names: a library that grows more expensive to keep current.
- **Symlinks are never followed** ([`requirements/scanning.md` §5](../requirements/scanning.md#5-behavior)). Stage 1 skips every symlink it lists, file or folder, without resolving it, and records a problem on it; the walk therefore needs no loop detection, and a symlink costs nothing to skip. The sidecar reader skips a symlinked sidecar. The watcher does not follow folder links either, and a scope reached through a link below its root, from the watcher or a plugin, is skipped whole with a problem, unless an exclude covers it, in which case it is treated as any other excluded scope (below). A file can become a link after the scan saw it, so before the server serves, resizes, or decodes a file it requires the file's real path to equal its root's real path joined with the stored relative path: a root reached through a link is allowed, a link anywhere below it is not found. **Known flaw:** a file swapped for a link between that check and the open can still be read; to be handled later.
- **Excludes cover every scope** ([`requirements/libraries.md` §1](../requirements/libraries.md#1-what-a-library-is)). Stage 1 does not descend a folder an exclude matches or pass on a file it matches, and a scope whose folder, or any folder between it and its root, matches one lists as empty, so a watch event or plugin request inside an excluded folder indexes nothing. Reconcile still runs on the scope's folder, listed as empty, so tracks indexed before their folder was excluded are marked missing, as a library scan marks them ([`requirements/scanning.md` §7](../requirements/scanning.md#7-change-handling)). An exclude pattern that does not compile suspends the scan before it touches anything, rather than scan what the admin excluded.
- **Stage 3 reads headers, never bodies.** Tags and technical properties live in the first and last kilobytes of a file. Nothing before stage 8 reads audio frames.
- **Stage 8 is a different queue on a different pool.** Indexing is what users wait for; analysis is not. Coupling them would make a cold scan wait on days of analysis.

## 3. Formats

**Format knowledge is quarantined in two places** — `probe`, which maps a file to a `Format`, and the tag mapper ([§4](#4-tags)). Nothing downstream knows what an ID3 frame or an MP4 atom is.

- **Extension is the first filter and costs nothing.** Discovery drops every path whose extension is not in the supported set before opening it. This is what makes "unsupported files are ignored, not flagged" ([`requirements/scanning.md` §1](../requirements/scanning.md#1-supported-formats)) free: documents, images, and archives are never touched.
- **Content confirms.** For files that pass the extension filter, the probe reads the magic bytes. A `.mp3` that is really a FLAC is read as FLAC; a `.flac` that is a text file is a `corruptAudio` problem, not a crash. MPEG audio is MP3 only when its frames are Layer III; a Layer I or II file named like MP3 is an `unsupportedEncoding` problem, and `.mp2` is not a candidate extension.
- **Two libraries cover the eight formats:**

| Format | Tags and properties | Decode |
|---|---|---|
| FLAC, Ogg Vorbis, Opus | lofty | ffmpeg |
| MP3 | lofty | ffmpeg |
| AAC/M4A, ALAC | lofty | ffmpeg |
| WAV, AIFF | lofty | ffmpeg |

- **ffmpeg decodes everything.** One decoder, one code path, one set of failure modes, and Opus covered — it has no mature pure-Rust decoder. The trade is a process boundary ([§11](#11-ffmpeg)), which is a feature here, not a cost.
- **lofty is the only tag reader.** ffprobe could read tags too, but it flattens multi-value fields, hides synchronized lyrics, presents embedded pictures as video streams, and spells keys differently per container — so it would have to be followed by a normalizer that re-derives what lofty already exposes. It also costs a process spawn per file, which at the Pi's roughly thirty files per second is feasible but spends most of the cold-scan budget on `fork`. lofty is in-process, structured, and covers all eight formats, so a file lofty cannot parse is a problem, not a fallback. WMA is out of the list for exactly this reason: it would have needed a second reader ([`requirements/scanning.md` §1](../requirements/scanning.md#1-supported-formats)).
- **A parser's panic is a bad file.** lofty parses untrusted files in-process, so a panic in it counts as a file it cannot parse: a `malformedTags` problem with a fixed detail, never the panic's message, which could name a host path. A panic reading an image header leaves that image out as artwork, as an unrecognizable image is.

## 4. Tags

**One canonical `TagSet`, whatever the scheme.** This is where "tag formats differ; results must not" ([`requirements/scanning.md` §2](../requirements/scanning.md#2-tags-are-the-only-truth)) is won or lost.

lofty exposes most fields through a scheme-independent key, which does the bulk of the work. The mapper handles what survives that abstraction — the places where schemes genuinely disagree:

| Field | Where schemes diverge |
|---|---|
| Album artist | `TPE2` (ID3), `ALBUMARTIST` / `ALBUM ARTIST` (Vorbis), `aART` (MP4) |
| Compilation | `TCMP` (ID3), `COMPILATION` (Vorbis), `cpil` (MP4) |
| Label | `TPUB` (ID3, which lofty reads as the publisher), `LABEL` / `ORGANIZATION` and `PUBLISHER` (Vorbis), `----:com.apple.iTunes:LABEL` (MP4) |
| Track and disc totals | packed as `3/12` in ID3 and MP4; separate `TRACKTOTAL` / `TOTALTRACKS` in Vorbis |
| Release date | `TDRC` (v2.4) vs `TYER`+`TDAT` (v2.3) vs free-text `DATE`; kept at tag precision ([`requirements/tracks.md` §2](../requirements/tracks.md#2-core-metadata)) |
| Multi-value | null-separated frames in ID3v2.4, repeated fields in Vorbis and MP4, semicolons everywhere |
| Lyrics | `USLT` / `SYLT` (ID3), `LYRICS` / `UNSYNCEDLYRICS` (Vorbis), `©lyr` (MP4) |
| Pictures | APIC frames, `METADATA_BLOCK_PICTURE`, `covr` atoms; front cover preferred by type |
| Identifiers | ISRC and MusicBrainz IDs under scheme-specific names ([`requirements/tracks.md` §6](../requirements/tracks.md#6-classification--identifiers)) |

- **Multi-value handling is one function.** Native repeated fields and semicolon-separated single fields both become the same `Vec<String>`, trimmed, empties dropped, order preserved ([`requirements/artists.md` §1](../requirements/artists.md#1-identity), [`requirements/tags.md` §3](../requirements/tags.md#3-multiple-values)). The semicolon is the only delimiter; nothing splits on "feat." or "&".
- **Unknown is a value.** A missing title becomes the filename stem; missing artist and album become `None`, which the core groups deterministically. The mapper never invents a value the file did not carry.
- **An absent album artist is the primary artist.** The `TagSet` keeps the album artists the file carries; `album_artists_or_primary` gives the ones its album takes: those, else none (the unknown artist) for a compilation, which its release type decides where it names a kind and its flag otherwise, else the first track artist ([`requirements/albums.md` §1](../requirements/albums.md#1-identity)). The scanner decides this once, and the store takes it.
- **Labels are the label tag's, then the publisher tag's**, in tagged order, each once: a label is dropped when an earlier one has the same name key (folded as an artist's is, [`database.md` §3](database.md#3-derived-data-the-scanner-maintains)), so a file carrying the same label in both tags, or in two spellings, has it once, as first spelled. The album takes those of its first track that has any.
- **ReplayGain tags are read and ignored.** Loudness is measured, not trusted ([`requirements/playback.md` §5](../requirements/playback.md#5-loudness)).
- **The golden corpus is the test.** One logical album is rendered into every supported format with identical logical metadata — multiple artists, a compilation flag, disc and track totals, a partial date, a label, embedded art and lyrics — and a test asserts the `TagSet` for each is byte-identical after serialization. Any new format or lofty upgrade runs against it.

## 5. Sidecars

**Sidecar resolution is per directory, not per file.** A thousand-track folder resolves `cover.*`, `artist.*`, and `artist.txt` once, not a thousand times.

- **A directory cache lives for the duration of a scan.** Keyed by directory, it holds which file of each sidecar kind the upward walk settles on ([`requirements/scanning.md` §3.1](../requirements/scanning.md#31-album-art)–[§3.3](../requirements/scanning.md#33-artist-biographies)). Walking stops at the library root ([§3.5](../requirements/scanning.md#35-resolution-rules)); parents are located lazily and memoized, so a deep tree costs one lookup per distinct ancestor.
- **Locating comes before reading, and sidecars are read only for files past stage 2.** Discovery's listing names a directory's sidecars with their sizes and mtimes, which settle which file of each kind applies to each directory and each track's stamp. Nothing is opened until a file that stage 2 did not skip resolves its directory; each located file is then read and hashed once per scan, so a rescan of unchanged music reads no sidecar.
- **The nearest sidecar that is there is the one that applies.** It must be a regular file, neither empty nor over 32 MB; among a folder's images of one kind the first such in extension order applies, so an empty `cover.jpg` gives way to the `cover.png` beside it. One that then fails to read as an image or as text is no sidecar, and the walk does not go on past it to the one above, so what a track resolves is exactly what its stamp hashes.
- **Lyrics are a same-directory filename match** with no walk ([§3.4](../requirements/scanning.md#34-lyrics)). The directory listing from discovery is reused; no second `readdir`. A name differing only in case (`.LRC`) is found through a lowercase index of the folder's lyrics files, built once per folder, so a folder of tracks without lyrics costs no pass over its listing per track.
- **Embedded wins, and is recorded as such.** A track with embedded art stores a reference to its own file's picture; one without stores a reference to the sidecar path that resolved. Both are *found* artwork; serving, resizing, and caching belong to [`requirements/conventions.md` §5](../requirements/conventions.md#5-imagery). Each track records its art, artist image, and biography, and albums and artists take theirs from their tracks ([`database.md` §3](database.md#3-derived-data-the-scanner-maintains)).
- **A sidecar change re-resolves the subtree.** The watcher ([§9](#9-triggers)) treats a change to a file matching a sidecar name as a scope covering its directory and all descendants, since anything below may have inherited from it ([`requirements/scanning.md` §7](../requirements/scanning.md#7-change-handling)). Stage 2 re-reads each track whose stamp changed, and the albums and artists those tracks reach follow.
- **The filenames are a public contract** that plugins write against ([`requirements/plugins.md` §3](../requirements/plugins.md#3-writing-to-the-library)). They are constants in one module and nowhere else.

## 6. Track Identity

**Deferred.** Content-derived identity that survives moves and retags ([`requirements/scanning.md` §6](../requirements/scanning.md#6-track-identity)) is open decision 3 in [`general.md` §11](general.md#11-open-decisions) and is not settled here.

Until it is, stage 4 keys on path: a file at a new path is a new track, and a file gone from its path is missing. This is wrong per the requirement and is understood to be temporary. Move identity is not built. What this design fixes now is where the stage sits, so the swap is contained:

- `identify` takes only what it uses today, the index row stage 2 found at the file's path, and returns new or updated. The identity that replaces it will take what stages 1–3 learned (path, size, mtime, device and inode, `TagSet`, `AudioProperties`, and the byte ranges of the tag regions, which any content fingerprint will need to skip) and the store, to tell a file moved from elsewhere, retagged, or with its audio replaced.
- Every file that is read reaches the identity stage; until identity is built, a file skipped at stage 2 or a known file that cannot be read keeps the track the index holds at its path without reaching it. Reconcile marks missing what the index holds at a path its folder no longer lists, so a track that identity has already moved is no longer held at its old path, and one marked missing before its new path is reached comes back when it is.
- The constraint the eventual design must meet: whatever it reads per new file has to keep a cold scan of a large library fast, which rules out hashing whole files at 500,000 tracks.

## 7. Persistence and the Change Feed

**Batches, not rows.** The scanner accumulates outcomes and hands the store a batch once it holds as many as the store can apply in about 50 ms, at least 16 and at most 250, or whatever has accumulated after 2 seconds, whichever comes first. One SQLite transaction per batch, which also saves the scan row with its cursor and progress, so no crash can leave the row behind or ahead of what the store holds. Every flush saves the row, even one whose batch is empty; only a scan's start and end save it on its own.

- **Unchanged files are not in the batch.** Reconcile compares each directory's listing with what the index holds in it ([§8](#8-reconciliation-and-missing-files)), so nothing records that a scan saw a file, and a rescan of an unchanged library writes no track. A directory's missing marks go in the batch with its files, and the cursor passes the directory only in the flush that persists them, so a resume reconciles again any directory whose marks were lost.
- **A batch can flush between any two files.** Before each file the scanner flushes once the batch is full or the 2 seconds have passed, so a flat folder of ten thousand files appears progressively too. The cursor names only folders whose every file is persisted ([§9](#9-triggers)), so a scan stopped partway through a folder walks all of it again on resume, and finds what it persisted unchanged at stage 2.
- **A store failure suspends the scan at its last persisted cursor.** The store either commits a batch whole or reports failure, and every question the scanner asks it can fail too: a directory's index read, the problems under a scope, saving the scan row. On any failure the scan row is rolled back to what the store actually holds and marked suspended, so a retry walks what was not persisted ([§9](#9-triggers)) and the admin sees a suspended scan rather than a clean one over lost work ([`requirements/scanning.md` §10](../requirements/scanning.md#10-problems)). If the store cannot save even that, the row keeps its last saved state and the next start resumes it as well. A read that fails is never taken for a directory of new files. A scan the admin had cancelled ends `cancelled` there instead, since it never resumes ([§9](#9-triggers)).
- **A panic anywhere else in a scan ends it the same way**, though only the roots it found not answering are retried ([§9](#9-triggers)), and the library's worker goes on to its next scan instead of dying with the scan still marked running. Only a parser's panic is a file's problem ([§3](#3-formats)): a panic in the store or the scanner is a bug, not a bad file.
- **Each batch appends to the library's change feed** ([`requirements/libraries.md` §5](../requirements/libraries.md#5-staying-current), [`general.md` §4](general.md#4-sync-and-mutations)). That is what makes content appear progressively: a client subscribed to the feed sees the first batch seconds after a scan starts, meeting the "first tracks browsable in seconds" budget.
- **The feed carries net effect, not events.** A track added and updated within one scan is one feed entry. This is the "large import does not flood clients" requirement: a ten-thousand-track import is a few dozen feed pages, not ten thousand notifications.
- **Albums and artists are derived inside the transaction.** Album identity is title plus album artists ([`requirements/albums.md` §1](../requirements/albums.md#1-identity)); the store upserts the album and artist rows a batch implies and drops any left with no tracks, so grouping is never stale between batches.
- **Sort keys are computed by the core** before the batch is written ([`general.md` §3](general.md#3-shared-core)). The store never sorts by anything but a precomputed key.
- **Writes yield to reads.** SQLite in WAL mode lets the browse and playback paths read while a batch commits.
- **Batches are sized by time, so interactive writes are not felt.** Plays, sign-ins and saves wait for the one writer behind a batch, and their confirmation must stay invisible ([`requirements/performance.md` §3](../requirements/performance.md#3-interactions)). How long a batch takes to build says nothing about how long it holds the writer, so the scanner times each apply, waiting for the writer and saving the scan row included, and sizes the next batch to apply in about 50 ms at the rate that one did. Part of a batch's cost does not shrink with it: its commit, and the recompute of each album it touches, which reads the whole album, so a batch touching an album of thousands of tracks (files with no tags at all share one) takes about 100 ms at 5,000 (laptop, debug build), more as the album grows, however few tracks it holds. Sized by time alone, such batches would fall to one track each and the scan would crawl, so a batch holds at least 16, and a scan's first batch, before anything has measured the store, is that size. From there batches grow to the right size within a few, and a slow one shrinks the next. Other costs are not sized either: a folder's missing marks go in whole with its last file, a folder gone from its listing is one range update however much lies under it ([§8](#8-reconciliation-and-missing-files)), and the problems a batch clears, one per path that scanned or listed cleanly, are not counted in its size (clearing 20,000 took 263 ms). On a 50,000-track database (debug build) a cold scan's batches went from 250 tracks in about 490 ms to 16–33 in a mean of 50 ms, for the same total apply time. Saving the scan row in the batch's transaction spares each of the nine times as many flushes a second commit: on btrfs a flush's fixed cost, one fsync'd commit, took about 4.5 ms, and saving the row in a transaction of its own after it made that about 8.5 ms and the scan 8–10% longer. The longest batch took 75 ms: SQLite's automatic checkpoint of its log runs in the commit that fills it, every third batch or so, and adds about 25 ms to it. Adding 1,000 tracks to an untagged folder of 5,000 took 5.4 s in batches of 16 at up to 105 ms, where batches of 250 took 1.5 s and batches of one, with no floor, 57 s.

## 8. Reconciliation and Missing Files

**Reconcile runs on each directory as the walk lists it, and marks nothing while the root does not answer.** The directory's listing is compared with the index read stage 2 made: each track directly in it whose file it no longer lists goes missing, and so does every track under a folder in it that it no longer lists. Both go in the batch with the directory's files. Problems are reconciled once per scope, after the walk.

- **An unavailable root suspends its scan and touches nothing.** Before walking, the scanner `stat`s the root. Failure — not mounted, permission denied, network gone — puts the scan in the `suspended` state and leaves every row under that root exactly as it was ([`requirements/libraries.md` §2](../requirements/libraries.md#2-storage), [`requirements/scanning.md` §7](../requirements/scanning.md#7-change-handling)). The failure mode being avoided: a NAS reboot at 3 a.m. marking 100,000 tracks missing. Once a wait has passed, a retry walks that root again ([§9](#9-triggers)), so a share mounted after the server started is indexed without a trigger.
- **A root that answered but returned an empty listing is treated as unavailable too.** A mount point with nothing under it is far more often an unmounted share than a deleted collection. The admin can override with a manual scan of that root, which is an explicit statement that the emptiness is real.
- **The root is checked again before anything is marked missing.** A directory whose listing lacks something the index holds marks it only if the root still answers. One that stopped answering suspends the scan the same way, leaving the rest of the scope for a retry, so a NAS that drops partway through, after which every directory lists as gone, marks nothing missing. The root is checked once more after the walk, before the problems under the scope are reconciled.
- **A folder gone from its parent's listing takes its subtree.** Each listing names the folders in it, and the index read names each folder in it under which a track lies. A folder the listing no longer names, as one deleted, renamed, excluded or replaced by a link, has every track under it marked missing with one range update, since the walk never reaches it. A Directory scope does this too, though it does not descend. **Known cost:** a folder whose tracks are all missing already is still in the index, so every scan of its parent names it as gone again and runs its range update, which marks nothing but reads every row under it: about 150 ms on a laptop for a renamed folder of 100,000 tracks. The cost lasts until the 30-day purge of missing tracks ([`requirements/scanning.md` §8](../requirements/scanning.md#8-missing-files)) removes those rows.
- **What the walk could not read keeps its tracks.** A folder that cannot be listed, or an entry that cannot be read, is a problem. A folder that cannot be listed is never reconciled, and its parent's listing still names it, so every track under it stays, even after a resume that no longer knows it failed. An entry that cannot be read keeps its track, or every track under it for a folder, and a listing that fails partway reconciles nothing of its own. Every other directory still reconciles, so one folder that is never readable, such as `lost+found`, doesn't stop the rest of the root from reconciling. A path that no longer exists is gone, not unreadable: a folder that vanished, even the scope's own, lists as empty with no problem, so what it held goes missing.
- **A known file that cannot be read keeps its track.** A file stage 3 cannot read is a problem, and one the index already holds keeps its track as well, seen by the scan and no longer missing, rather than being marked missing and coming back once it reads. The track keeps its tags. A file whose size or mtime changed makes the track forget its mtime, so no file matches it, not even the last one read restored from a backup that kept its time, and stage 2 reads the file again on every scan, as it does a file with no track, until a clean read updates the track and clears the problem ([`requirements/scanning.md` §10](../requirements/scanning.md#10-problems)). Nothing short of that read, such as a stat, a move away and back, or a background job opening the file, can leave the old tags standing with no problem past the next scan. One read only because its lyrics file changed keeps its size and mtime.
- **Problems go with what is gone.** Reconcile also asks the store for the problems recorded in the scope and clears those whose path no longer exists. A problem on a path that is still there stays until that path scans or lists cleanly ([§13](#13-progress-and-problems)), because the walk cannot tell whether a cause it did not look at, such as a failed decode, is fixed.
- **Missing is a mark, not a delete.** Reconcile sets `missing_since` on the tracks the listings no longer show. Retention is store policy per [`requirements/scanning.md` §8](../requirements/scanning.md#8-missing-files), not the scanner's: the database writer's hourly sweep purges a track missing for 30 days ([`database.md` §9](database.md#9-retention)). Playlist pinning and immediate cleanup are not built yet.
- **A returning file clears the mark** in stage 2: a path that matches a missing row with the same size and mtime is a return, not an add.

## 9. Triggers

**One scanner task per library owns one coalescing queue of scopes.** A scope is a root or a folder within one. Every trigger — the filesystem watcher, the schedule, a manual request, a configuration change, a restore — does nothing but enqueue a scope. This is how "overlapping triggers never compound" ([`requirements/scanning.md` §4](../requirements/scanning.md#4-triggers)) is made structurally true rather than defended case by case.

- **A scope has a depth.** A *directory* scope visits only the files directly in a folder, which is what an ordinary file change produces; a *subtree* scope descends. Roots, manual folder scans, directory events, and sidecar changes are subtree scopes.
- **Enqueue coalesces into queued scans only.** A scope covered by a queued scan that has not started joins that scan. A scope that contains queued scopes replaces them. A running scan takes no new work, even work it covers, since its walk may already have passed that folder and a reconfiguration must apply its new excludes. That work queues a scan behind it, which later triggers it covers join; work in another folder queues its own scan, until a library scan replaces them all. Returning the equivalent queued scan is therefore a lookup, not a special case. The queue decides under its lock and writes the scan rows after, the new scan's before those of the scans it replaces, so a busy store holds up only the trigger writing, never the worker or a progress read, and a crash between the writes leaves the replaced work queued rather than lost. A request that finds, once its row is written, that another request has meanwhile queued a scan covering its work cancels its own row and joins that scan. Cancelling a queued scan writes its row outside the lock too; a cancel the store cannot save puts the scan back after the last scan still queued that was ahead of it.
- **The watcher is `notify`, debounced.** Events are grouped by directory over a window of about two seconds and enqueued as one scope per directory, so a copied-in album is one scope, not one per file. Sidecar-named files widen the scope to the subtree ([§5](#5-sidecars)). A path that no longer exists enqueues its folder, and its own subtree too when it was a folder: one the event reports as a removed folder, or, for a rename, one under which the index holds a track or a problem. A renamed folder's old tracks are therefore marked missing as the new ones are added, while deleting or renaming many files in a folder is still one scope, not one per file. Watcher overflow or error enqueues the whole root — the watcher is a hint, never the source of truth — and an overflow walks every root again too, so a folder whose event was dropped is watched. The watcher starts on its own thread once the server is listening, so a large library delays nothing, and a shutdown waits at most a second for it. Each root has its own watch, which costs one inotify instance (Linux allows 128 per user by default). The watch is our own walk, not `notify`'s recursive one, which stops at the first folder it cannot watch: it watches each folder the scan walks on its own, before listing it, so a folder made meanwhile is still seen. An excluded folder (by the library's excludes as the watcher starts), a link, and a folder that cannot be read, such as a root-owned `lost+found`, are not watched, as the scan leaves them out too. A folder made or moved in is watched, with the folders below it, as its event arrives. Each root's watch remembers the folders it passed over as unreadable, usually none or a `lost+found`; a change of permissions at or above one tries that folder again, so one made readable is watched from then on, while any other change of permissions walks nothing. A root whose only unwatched folders are ones the scan cannot read either counts as wholly watched: nothing the scan could index goes unseen, and the scan reports each such folder as a problem. It is not wholly watched when the OS limit on watches stops a folder, which ends the walk, since every later folder would meet it too, or when the root, or a folder the scan reads, cannot be watched for another reason, as when a security policy refuses only the watch. Each root logs whether its watch covers the whole root or why not. Every ten seconds the watcher checks that each root is still the directory, by device and inode, that it watches. One that is not, as when a share is mounted over it or unmounted from under it, is watched afresh, and so is one whose watch failed short of the OS limit. A fresh watch that meets the limit is tried once more, since the watches it replaced are let go a moment after it starts. A root watched wholly afresh is scanned, since what changed while it was not watched was missed. Each fresh watch of a root holds off the next for a wait that doubles, up to an hour, until the root has stayed as it was watched for a whole wait, so a flapping mount is scanned less and less often rather than at every check. **Known gap:** a share unmounted and mounted again between two checks with the same device and inode, which NFS, SMB, FUSE and ext4 roots can do, goes unnoticed, since `notify` passes on neither inotify's unmount event nor the end of a watch, and its root stays unwatched until a restart. Its dead watch still counts as whole, so no fallback starts: only a schedule the admin set covers it.
- **The schedule enqueues the whole library** on the admin's interval. It is the safety net for network mounts where `inotify` does not fire ([`requirements/deployment.md` §3](../requirements/deployment.md#3-storage--permissions)). A watched library with no interval is scanned daily while any root is not wholly watched, and the log says so.
- **Manual scans are the API enqueuing a scope** with visible progress, which is the queue's own state ([§13](#13-progress-and-problems)).
- **Resumability is a cursor.** Discovery walks in a stable sorted order and the scan row records the last directory fully persisted, in the transaction that persists it ([§7](#7-persistence-and-the-change-feed)). A graceful shutdown stops the running scan after the file in hand and flushes what it holds, but writes no final state, so the row stays `running` at its cursor, and queued scans stay `queued`: an upgrade in the middle of a scan resumes exactly as a crash does. On restart, every scan in `running` resumes from its cursor; a scan row that cannot be read is logged, marked suspended, as it can never resume, and left out, and the others resume. A scan the store cannot record is not queued; its work waits to be retried as a suspended scan's does (below). A watched folder whose index the store cannot check is scanned, as if it held tracks. A resumed scan takes no new work, even while it waits in the queue, since its walk has passed everything before its cursor: work it covers queues a new scan, and a new scan that covers the resumed scan's scopes replaces it, as the startup library scan does. A resumed scan needs no memory of what it could not read before its cursor, since a folder it could not list is never reconciled ([§8](#8-reconciliation-and-missing-files)). It does not reconcile again the folders it passed before its cursor, so a folder deleted while it was interrupted, under one of those, keeps its tracks until the next walk of its parent; the startup library scan that replaces a resumed scan not yet started is one. A suspended scan's work is retried as a new scan, never resumed, so a folder it ended in, counted as it stopped, is not counted again. The server's startup library scan covers every resumed library scan and replaces it unless the worker has already started it, so after any restart every root is walked again, which it must be, since nothing watched while the server was down. That scan is `scheduled`, since `initial` names a library's first scan: a library none of whose scans has completed gets an `initial` one instead. Already indexed files then cost only the stage-2 check, so nothing persisted is read again.
- **A cancelled scan stops after the file in hand** and ends `cancelled`, even when a shutdown comes before it stops, so it never resumes. Everything persisted stays persisted; the store is never rolled back to before the scan.
- **Work a suspended scan left undone is retried after a wait.** A suspended scan never resumes. It leaves undone each scope whose root did not answer, before its walk or before its reconcile, and, when the store failed, every scope from its last persisted cursor on. That work waits a minute, then is queued as a new scan of just those scopes, with the trigger of the scan that left it, joining or replacing queued scans as any trigger's work does. A new scan rather than a resume, since a scope whose root went before its reconcile may lie behind the cursor that a later scope moved, and no resume would walk it again. Each later wait is twice as long as the one before, up to thirty minutes, until a scan completes the retried work, so a share that stays unmounted costs a root check now and then, not a scan loop, for as long as it stays away. Work the store failed on is retried too, and a scan covering what a retry queued is its retry: once six retries in a row of that work have failed on the store again, about an hour of waits, the failed work they covered is dropped with an error in the log to wait for the next trigger, since a failure that recurs at the same file would otherwise walk most of a root again every half hour. A retry that ends without a store failure starts the count again, and work no retry covered, such as a trigger's that the store could not record, waits whatever else has failed. A panic leaves nothing to retry but the roots found not answering before it, since it is a bug that would recur. A library holds one retry at a time: work left undone while a retry waits joins it and keeps its time, and a scan that starts covering the waiting work, such as a scheduled one, does it in the retry's place, unless it resumes from a cursor that may lie past some of that work. A scan suspended by an exclude pattern that does not compile leaves nothing undone, since its retry would suspend at once too; a reconfiguration scans the library anyway, and a retry queues no work in a root it removed. A shutdown is not a suspension: the running scan stays `running` for the next start to resume, and the retry waiting is forgotten, since the startup scan covers it. What suspended a scan stays in the log, as the API has no field for it.

## 10. Priority and Pacing

**Scanning yields to listening** ([`requirements/scanning.md` §5](../requirements/scanning.md#5-behavior), [`general.md` §2](general.md#2-system-shape)).

- **Indexing runs on a small dedicated blocking pool** — discovery, `stat`, and tag reading are synchronous I/O and never touch the async runtime's workers. Pool size defaults to one on the Pi and a few on the desktop; storage is the bottleneck either way.
- **Background work runs on one pool for the whole host.** Every library's analysis and its placeholders ([§12](#12-analysis)) are a job each, and one pool of threads runs them all. Its size is half the host's cores, at least one, so two on a four-core Raspberry Pi and eight on a 16-thread desktop ([§16](#16-open-decisions)), and with more than one library it has one thread beyond that. Each thread runs one pass of one job at a time, and so one ffmpeg child, which makes the pool's threads the only bound on background ffmpeg: without one, every library could decode a 64-megapixel cover at once, at about 400 MB each. The threads take the jobs that are due in turn, so one library's backlog never starves another's. A job with work stays due, so a library with the most to do gets the threads the others leave free, each pass taking a file no other pass has in hand; a job whose pass found nothing or backed off waits, 30 seconds for analysis and 5 for placeholders, without holding up the rest. One library's failure stays its own. A pass that panics is logged and its job waits as an idle one does, at no cost of a thread. No library runs on more threads at once than the pool's size, so with more than one library, one whose passes hang, as on a dead hard-mounted share, leaves the thread beyond it for the others, while a library busy alone keeps the whole size. That thread costs one more ffmpeg child, only while two libraries have work at once.
- **Background work runs at low priority.** The pool's threads each lower their own priority by 10 nice steps when they start, and the ffmpeg children they spawn inherit it, since on Linux niceness belongs to a thread. Request handling, the artwork resize, and transcodes keep normal priority. A nice-10 task carries about a tenth of a nice-0 task's weight with the scheduler, so under contention listeners get most of the CPU and background work slows down without stopping: pinned to one core with four busy nice-0 processes, a nice-10 decode got about 5 to 10% of it. The stall watchdog counts the CPU time a child uses, so a child slowed this way is not taken for stalled ([§11](#11-ffmpeg)). Elsewhere than Linux, background threads keep their priority, since lowering it would lower the whole process.
- **Nothing pauses.** Stopping ffmpeg with `SIGSTOP` would freeze a transcode mid-stream, so interactive work (the artwork resize, and transcodes) runs outside the background pool, and no signal but its own caller's ever reaches it.
- **Nothing here decides what a listener gets.** If the host cannot serve a new stream, that refusal belongs to the playback design.

## 11. ffmpeg

**ffmpeg runs as a child process, never linked as a library.**

- **Isolation is the reason.** Corrupt files are routine in real collections. A decoder crash inside the server would violate "one bad file never aborts a scan" ([`requirements/scanning.md` §10](../requirements/scanning.md#10-problems)) and take listeners down with it. A child that dies is a problem record, and a child that hangs is killed. Neither is available in-process.
- **Build simplicity is the second reason.** No `bindgen`, no cross-compiling libav for `arm64`, no linking questions. The container installs a pinned ffmpeg for both architectures.
- **The cost is a spawn per file and a pipe of PCM.** Negligible for analysis, which is budgeted in days, and for transcodes, which are per stream.

The `ffmpeg` crate runs three background operations in one pool:

| Operation | Invocation (illustrative) | Used by |
|---|---|---|
| `probe(path)` | `ffprobe -v error -print_format json -show_streams -show_format -max_pixels 67108864 -protocol_whitelist file -i file:<path>` | analysis setup — the sample rate and channel layout that interpret the PCM stream, and the duration ([§12](#12-analysis)) |
| `decode_pcm(path)` | `ffmpeg -nostdin -v error -max_pixels 67108864 -protocol_whitelist file -i file:<path> -map 0:a:0 -vn -ch_layout <layout> -ar <rate> -f f32le -c:a pcm_f32le pipe:1` | analysis |
| `decode_image(path, size)` | `ffmpeg -nostdin -v error -max_pixels 67108864 -protocol_whitelist file -i file:<path> -map 0:v:0 -frames:v 1 -vf scale=… -f image2pipe -c:v pam -pix_fmt rgba pipe:1` | placeholders — the image, or a track's attached picture, scaled to fit 100 pixels |

Interactive work, which a listener waits on, runs outside the pool. The crate only builds its command, and the caller spawns it under its own bound and timeout, at normal priority, so a request never waits behind analysis. The server's artwork resize is `resize_command(path, size)`: `ffmpeg -nostdin -v error -max_pixels 67108864 -protocol_whitelist file -i file:<path> -map 0:v:0 -frames:v 1 -vf scale=… -f image2pipe -c:v mjpeg -q:v 3 pipe:1`, one JPEG behind the same input guards. `transcode(path, target)` will be built the same way, as the playback design specifies.

- **A stall is measured in CPU time.** Once a second the watchdog adds to each pooled child's time without progress, and kills a child past 30 seconds. A PCM decode makes progress with every read of its output; a probe or an image decode makes none, so for them the 30 seconds bound the whole run. A child that is running or waiting for a CPU (state `R` in `/proc/<pid>/stat`), or whose CPU time rose, which covers a decoder whose own threads run while its main thread waits on them, adds the CPU time it got, at most the time that passed. Any other child is blocked, and adds the time that passed. A child blocked for good therefore dies after 30 seconds, and one spinning without output after 30 seconds of running, but one starved by busier work is not killed: at nice 10, pinned to one core with four busy nice-0 processes, a 3000² PNG decode that needs 0.4 s of CPU took 6 to 8 seconds, and a 6000² one that needs 1.5 s took 19 to 27, on a laptop several times faster than the Pi. Off Linux, where there is no `/proc`, the time that passes counts.

- **Every invocation is read-only against the library.** No output path is ever under a root; `-nostdin` is always set; there is no `-y`. The music mount is usually writable, for plugins ([`general.md` §2](general.md#2-system-shape)), so this rule is the defense.
- **Every input is a local file.** Each invocation names its input `file:<path>` with `-protocol_whitelist file`, so a path that starts with `-` or looks like a URL is still read as a file, and a container that names further inputs, such as an HLS playlist, can open only local files. A name containing `%d` may be read as an image sequence.
- **Every input refuses pictures over 64 megapixels** (8192², which admits a 600-dpi LP scan). `-max_pixels` refuses a small file that declares a huge picture before its pixels are allocated. That includes an audio file's attached picture, which a probe and an audio decode read too: they skip it, and the audio still decodes. A placeholder or a resize exits with an error, which is remembered and not tried again on every request.
- **Startup verifies the binary.** The server runs `ffmpeg -decoders` once, checks that every decoder the format list requires is present, and logs its version and a warning naming any format it cannot decode. Showing this in the admin interface's library health ([`requirements/deployment.md` §7](../requirements/deployment.md#7-observability)) is not built yet. A missing decoder is one startup message, not ten thousand scan problems at 3 a.m. Missing ffmpeg entirely is fatal at startup, in the spirit of "bad configuration fails loudly" ([`requirements/deployment.md` §1](../requirements/deployment.md#1-what-the-user-provides)).
- **Exit status and stderr map to problem kinds.** A nonzero exit with a decoder error is `corruptAudio`; an unknown codec is `unsupportedEncoding`; a kill on timeout is its own group. Stderr is drained while the child runs, so a decoder that logs an error per damaged frame never blocks on a full pipe, and its last 4 KiB becomes the problem's detail.

## 12. Analysis

**One decode, every consumer** ([`requirements/scanning.md` §1](../requirements/scanning.md#1-supported-formats), [`requirements/performance.md` §5](../requirements/performance.md#5-scanning--analysis)).

`decode_pcm` streams interleaved 32-bit float at the file's native sample rate and channel layout, which the probe supplies so the raw stream can be interpreted. The decode is held to the probe's shape: `-ar` and `-ch_layout`, or `-ac` for a stream that names no layout, make ffmpeg convert any part of the file in another shape (a mono intro joined to a stereo MP3, say) rather than hand back samples the probe would misread. The layout is named rather than counted because ffmpeg reads a bare count as its default layout and would remix quad or 6.0 into it. The scanner reads that stream once, in blocks, and feeds every block to each sink:

- **Loudness** — an EBU R128 meter (the `ebur128` crate) over the full channel layout, yielding integrated loudness and true peak. Measured at native rate and layout, so multi-channel and high-resolution files are measured as what they are ([`requirements/tracks.md` §4](../requirements/tracks.md#4-audio-properties)). Album loudness is aggregated by the store from the album's tracks, not by a second decode.
- **Waveform** — a mono downmix bucketed into a fixed number of bins per track, each storing its RMS as a level on a log scale: a byte counting half decibels up from 127.5 dB below full scale, so 255 is full scale and 0 is silence. The stored levels are the honest measurement. The server shapes them for legibility ([`requirements/playback.md` §3](../requirements/playback.md#3-the-waveform)) with one function in `core`, in integer math so the same levels give the same points on every machine. The 5th and 95th percentiles of the track's own sounding bins draw at a floor that keeps the quietest passage visible and at full height, with the levels between placed linearly in decibels, so a compressed master and an orchestral recording are each scaled to their own dynamics. Those percentiles are taken at least 6 dB apart, so a track of nearly constant loudness does not draw small differences as large ones. A silent bin draws nothing, and a louder bin never draws lower than a quieter one, so shaping invents no structure and moves no transition. The bin count is the playback design's to fix.
- **Features** — not built yet: tempo, key, energy, and a compact sonic descriptor over a mono, downsampled copy of the same blocks ([`requirements/recommendations.md` §2.1](../requirements/recommendations.md#21-how-the-music-sounds)). The extractor and its storage are the recommendations design's choice; the scanner's contract is only that it becomes a third sink on the same block stream and adds no second pass.

Storage and scheduling:

- **Results live in `state/`, not `cache/`.** They are rebuildable in principle, but rebuilding costs days ([`general.md` §2](general.md#2-system-shape)); losing them to a cache purge would be an outage. They are keyed by track and versioned by analyzer version, so a release that changes an algorithm reprocesses in the background ([`requirements/deployment.md` §5](../requirements/deployment.md#5-upgrades)) rather than requiring a rescan.
- **The analysis queue is a store query, not an in-memory list.** "Tracks whose results come from an older analyzer version than the current one" is the queue, where a track never analyzed is at version 0; a restart loses nothing. A track being analyzed when the process dies is simply analyzed again. The store takes tracks never analyzed first, then those an older analyzer did, newest first within each ([`database.md` §8](database.md#8-scanning-state)).
- **Priority within the queue favors what will be heard.** Tracks in a playing or queued context and tracks recently added go first; the long tail follows. This is what makes a two-day analysis feel finished within an hour for the music people actually play.
- **A scan that finds a file's size or mtime changed queues its track again.** Neither says whether the audio or only the tags changed, so the upsert puts the track back at version 0, clears its loudness and peak, and deletes its waveform, and the album's loudness is recomputed from the tracks still analyzed. A retag therefore costs one more decode of that file, in proportion to the change. A known file whose size or mtime changed but which cannot be read is put back at version 0 the same way, since its results measured other audio, and the queue leaves a track whose mtime is unknown ([§8](#8-reconciliation-and-missing-files)), so analysis does not open the file, and clear its problem, before a scan has read it. One that cannot be read with its size and mtime unchanged, read only because its lyrics file changed, keeps its results. A lyrics file appearing beside an unchanged track re-reads it but keeps its results, so lyrics a plugin adds across the library queue nothing. A result is stored only while the file's size and mtime are still those its track was picked with, so a track whose file is replaced during its decode does not take the old audio's measurements.
- **A file judged broken gets an empty result at the current version**, so it is not retried on every pass. The failure is recorded as a scan problem, and a later scan that finds the file changed queues it again, as above.
- **Only a verdict on the file is stored.** That is a decoder's error on a file that still opens, a symlink refused (one leading nowhere included), anything but a regular file refused (a pipe would block the decoder forever), or a second failure of the file of a kind that may pass (a stall, a decoder killed by a signal) with no success of it between, so one file cannot hold up the queue. Another file failing or decoding between does not count, since passes running at once interleave them.
- **A file that cannot be opened never gets a result.** Gone, out of reach, not permitted, or under a dropped sub-mount, it is recorded as an `unreadable` or `permissionDenied` problem and skipped for an hour while the queue moves on; the skip list is per job and library and in memory, so a restart tries again. Reachability is an open, not a stat: an open fails on a file that may not be read, and NFS revalidates it. Once the file opens, it is decoded as usual, and its problem is cleared, even one recorded before a restart.
- **Everything else backs the job off** with nothing recorded, for that library alone: an unavailable root, a decoder that cannot start, a first failure that may pass, or a store error, which leaves the file as it was, so a file whose problem could not be recorded does not wait out the hour. A NAS outage therefore never strips results from the tracks it hid. Placeholders follow the same rules.
- **Each track is independent.** A kill or a timeout affects exactly one track. The only state a job keeps across tracks is the skip list, the files that failed once, and the files its passes have in hand, all in memory and per library.

## 13. Progress and Problems

- **Progress is the scan row.** `filesSeen`, `filesProcessed`, added, updated, moved, missing, problems, and the current path are updated on the scan row at each batch, which the admin API reads directly ([`api/openapi.yaml`](../api/openapi.yaml), `Scan`). There is no separate progress channel to keep in sync.
- **The counts match the cursor**, so a resume counts no file twice ([§9](#9-triggers)). A track added or updated is counted as it is batched, since a resume finds it unchanged; the files seen in a folder and its problems, and a folder that could not be listed, are counted once the cursor passes them, since a resume meets them again. Partway through a large folder, `filesProcessed`, added, and updated can therefore run ahead of `filesSeen`. A scan that ends never resumes, so it counts any folder it could not list as it ends, and a cancelled one also what it saw of the folder it stopped in, unless a failed batch or a panic ends it first, which leaves the counts last flushed. A retry of what a suspended scan left undone counts what it meets again for itself.
- **Problems are grouped by a stable key** — kind, root, and a normalized detail with paths and numbers stripped — so a permissions error on one root is one group with a count, not ten thousand rows ([`requirements/scanning.md` §10](../requirements/scanning.md#10-problems)). Individual occurrences are kept under the group for the drill-down endpoint.
- **A successful scan of a file, or listing of a folder, clears its problems** in the same batch that persists it, and reconcile clears those of paths that no longer exist ([§8](#8-reconciliation-and-missing-files)). The count on the group falls, and an empty group is removed.
- **A scan that had problems says so.** The scan row records the problem count; the library health view shows outstanding groups. A partial result is never reported as a clean scan.

## 14. Duplicates

**Not built yet.** It will be a background job over the index, never part of a scan ([`requirements/scanning.md` §9](../requirements/scanning.md#9-duplicates)).

- **Matching tags** — same title, artists, album, and track number; a store query.
- **One album under two paths** — same album identity spanning two directories, where those directories are not the discs of one album (`CD1`, `CD2`); a store query.
- **Matching content** — awaits track identity ([§6](#6-track-identity)); whatever fingerprint identity adopts, duplicates by content is an equality query on it.

The job will run on the indexing pool at the lowest priority, write only to a duplicates table, and never touch a track row. The report is the API's `DuplicateGroup`.

## 15. Verification

- **Golden corpus** ([§4](#4-tags)) — identical logical metadata in every format yields identical `TagSet`s; run on every build and on every lofty or ffmpeg upgrade.
- **Generated library** — the `bench/` generator emits a large library with realistic tag variety, sidecars at every level, and a fraction of deliberately corrupt files. Cold scan, ten-file incremental, and copied-in-album latency are measured against [`requirements/performance.md` §5](../requirements/performance.md#5-scanning--analysis) at p95 and p99.
- **Pipeline suite on the real store** — the pipeline scenarios, the scanner's own, run as one suite against the server's SQLite store, the only real `Store`, including those that make the store slow, fail it, or hold a scan up partway. Store-only cost on a development laptop, in release: inserting 50,000 synthetic tracks with all derived data took 11 s, which extrapolates to roughly two minutes at 500,000. An unchanged rescan writes no track; the same benchmark times the one index read per folder it makes instead. Measurements on low-power hardware decide, but the store is not where a cold scan's time goes.
- **Fault injection** — a root unmounted mid-scan leaves the index intact and the scan suspended; a hung ffmpeg is killed within its timeout and recorded; a kill or a graceful stop of the server mid-scan resumes from the cursor with no duplicate rows and no missed files.
- **Isolation** — a scan of one library never reads a path under another library's root and never writes a row outside its library ([`requirements/general.md` §3.6](../requirements/general.md#36-libraries-are-the-isolation-boundary)).
- **Read-only** — the whole suite runs against a read-only mount and passes.

## 16. Open Decisions

1. **Track identity** ([§6](#6-track-identity)) — open decision 3 in [`general.md` §11](general.md#11-open-decisions). This design fixes where the stage sits and its budget, not its algorithm or its inputs.
2. **Waveform bin count** — the playback design's, constrained here to be derived from the one decode with no second pass.
3. **Feature extractor** — the recommendations design's, constrained here to consume the shared block stream.
4. **Background pool size** — one pool for every library, at half the host's cores, plus one with more than one library ([§10](#10-priority-and-pacing)); benchmarks on low-power hardware decide the shipped value.
